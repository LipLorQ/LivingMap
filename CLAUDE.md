# CLAUDE.md — правила работы Claude Code с проектом LivingMap

Этот файл обязателен к чтению перед любыми изменениями в репозитории.

## 1. Источники истины

Перед началом любой задачи Claude Code обязан прочитать целиком:

1. `DEVELOPMENT_PLAN.md` — источник истины по порядку разработки, границам этапов и Definition of Done.
2. `ARCHITECTURE.md` — источник истины по технической архитектуре и границам системы.
3. Этот `CLAUDE.md`.

Если старый код, старый prompt, старый roadmap, комментарий или прежнее техническое решение противоречит этим документам, нельзя молча продолжать по старой версии.

При конфликте:
- остановиться;
- явно описать противоречие;
- предложить минимальное решение;
- не менять канон без подтверждения пользователя.

## 2. Перед началом работы

До изменения кода:

1. Найти корень репозитория.
2. Проверить `git status`.
3. Проверить текущую ветку и remote.
4. Проверить последние commits.
5. Определить текущий утверждённый этап по `DEVELOPMENT_PLAN.md`.
6. Кратко перечислить:
   - что относится к текущему этапу;
   - что относится к будущим этапам и поэтому сейчас НЕ делается.
7. Изучить существующий код до создания новых сущностей или переписывания работающего фундамента.

Не уничтожать и не перезаписывать незакоммиченные пользовательские изменения.

## 3. Работа только в границах текущего этапа

Не добавлять функции по принципу «раз уж мы здесь».

Перед любой дополнительной работой задать вопрос:

> Это необходимо для Definition of Done текущего этапа?

Если нет:
- не реализовывать;
- при ценности записать идею в `FUTURE_IDEAS.md`;
- продолжить текущий этап.

Claude Code не переходит к следующему этапу самостоятельно.

## 4. Документация обязана отражать реальность

Если в ходе согласованной работы фактическая реализация уточнила техническое решение:

- обновить соответствующий ADR;
- обновить `ARCHITECTURE.md`, только если реально изменилась или уточнилась каноническая архитектура;
- обновить `DEVELOPMENT_PLAN.md`, только если пользователь отдельно согласовал изменение плана;
- не менять канонические документы ради косметики.

Код и документация не должны расходиться.

## 5. Завершение этапа

Этап считается завершённым только когда одновременно:

1. выполнен его Definition of Done;
2. проходят необходимые lint / typecheck / unit / integration / E2E проверки;
3. проверен реальный сценарий этапа;
4. проведён независимый code review, если он предусмотрен задачей;
5. исправлены high severity и разумные in-scope замечания;
6. пользователь явно подтвердил завершение этапа.

Написанный код сам по себе не означает завершение этапа.

## 6. Git и GitHub

GitHub-репозиторий `LipLorQ/LivingMap` является постоянным хранилищем актуального состояния проекта.

После каждого **согласованного завершённого этапа** Claude Code обязан:

1. ещё раз проверить `git status`;
2. обновить документацию, которую реально затронули изменения;
3. убедиться, что секреты, локальные БД, токены и временные файлы не попадут в commit;
4. запустить обязательные проверки;
5. сделать осмысленный commit завершённого этапа;
6. push в настроенный `origin`.

Не пушить незавершённый следующий этап как завершённый.

Если push невозможен:
- не скрывать ошибку;
- показать точную причину;
- оставить локальный commit целым;
- дать минимальную инструкцию для исправления.

Не использовать force-push без отдельного явного разрешения пользователя.

## 7. Коммиты

Коммит должен описывать законченный смысловой кусок, а не случайный набор файлов.

Предпочтительные примеры:

```text
chore: establish architecture spike
feat: complete local foundation
feat: add first real intention model
docs: update architecture after validated change
fix: prevent stale MCP overwrite
```

Не создавать фиктивные «stage complete» commits, если Definition of Done не выполнен.

## 8. Безопасность данных

Никогда не коммитить:

- OAuth tokens;
- API keys;
- SSH private keys;
- содержимое production/local SQLite DB;
- личные секреты пользователя;
- временные backup-файлы, если они содержат реальные пользовательские данные;
- `.env` с секретами.

Все такие пути должны быть закрыты через `.gitignore` или другой подходящий механизм.

## 9. Финальный отчёт после задачи

В конце каждой существенной задачи сообщить:

- текущий этап;
- что изменено;
- какие файлы изменены;
- какие проверки выполнены и их результат;
- что осталось незакрытым;
- был ли создан commit;
- был ли выполнен push;
- можно ли переходить дальше.

После этого остановиться, если следующий этап требует подтверждения пользователя.

## 10. Главное правило

> `DEVELOPMENT_PLAN.md` определяет **что и когда строим**.  
> `ARCHITECTURE.md` определяет **как устроен технический фундамент**.  
> `CLAUDE.md` определяет **как Claude Code обязан работать с проектом**.

Ни один новый контекст Claude Code не должен начинать работу, не прочитав эти три файла.
