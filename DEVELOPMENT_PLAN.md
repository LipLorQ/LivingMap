## 0. Зачем существует этот документ

Этот файл фиксирует **конечный порядок разработки текущего MVP Живой карты**.

Старый план разработки больше не является основанием для работы. Если старый roadmap, старый prompt, прежняя спецификация или будущий контекст Claude Code противоречат этому документу в вопросе **порядка разработки и границ этапов**, источником истины считается этот файл.

План не меняется просто потому, что по ходу разработки появилась «хорошая идея». Он меняется только если:

1. фактическое использование показало, что предположение было неверным;
2. обнаружена техническая блокировка, делающая текущий этап невозможным;
3. изменилось продуктовое решение пользователя;
4. новая информация делает текущий путь объективно нерабочим.

Любое такое изменение сначала описывается как предложение. Claude Code не меняет roadmap самостоятельно.

# 1. Что мы строим

Главная сверхспособность Живой карты:

> **Превращать большие желания в реально завершённые результаты.**

Пользователь выбирает, какую жизнь строить.

ИИ понимает контекст, помогает построить путь, определяет порядок следующих действий и перестраивает его при изменении реальности.

Живая карта:

- хранит актуальную реальность;
- хранит долгую память;
- хранит ограничения;
- показывает один текущий ход;
- позволяет увидеть порядок;
- проводит человека через исполнение;
- фиксирует результаты;
- возвращает прожитое обратно в будущие решения.

Ключевая петля продукта:

**Замысел → ИИ строит путь → пользователь подтверждает → ИИ определяет порядок → реальность фильтрует допустимое → Живая карта показывает одно `Сейчас` → пользователь делает → состояние меняется → ИИ при необходимости перестраивает порядок → Замысел приближается к завершённому результату.**

# 2. Первый пользователь и текущие ограничения

Первый пользователь — **Ева**.

На первых месяцах продукт можно оптимизировать под её реальное использование без попытки заранее сделать универсальный SaaS.

- работает локально на Windows;
- запускается только когда пользователь открывает её;
- не обязана работать 24/7;
- не требует сервера;
- не требует аккаунта;
- не требует мобильного приложения;
- не требует облачной синхронизации;
- не требует собственного ИИ API;
- использует подписочный Claude / ChatGPT через MCP там, где это поддерживается;
- должна оставлять техническую возможность будущего расширения до desktop + web/mobile + аккаунтов.

Принцип:

> **Оставить двери для будущего продукта, но не строить за ними инфраструктуру заранее.**

# 4. Канонические продуктовые решения

## 4.1. Роль ИИ

ИИ является обязательной частью **полного продукта**, а не декоративным помощником.

В текущей локальной версии основной сценарий:

**пользователь открывает Claude / другой совместимый ИИ → ИИ подключается к Живой карте через MCP → читает разрешённый контекст → предлагает или изменяет разрешённые сущности.**

Живая карта не должна притворяться ИИ там, где нужен настоящий анализ.

## 4.2. Кто выбирает `Сейчас`

ИИ определяет **порядок** действий.

Живая карта проверяет объективные ограничения:

- блокировки;
- выполненность;
- сроки;
- доступное окно времени;
- события календаря;
- статус действия;
- подтверждённые пользовательские ограничения.

После проверки Живая карта показывает **первый допустимый ход** как `Сейчас`.

> **ИИ выбирает порядок. Реальность ограничивает. Интерфейс показывает одно.**

Пользователь может раскрыть весь текущий порядок.

## 4.3. Стратегические решения остаются у пользователя

Без подтверждения пользователя нельзя:

- менять большую картину жизни;
- менять годовой курс;
- менять сезон;
- менять условия хорошей жизни;
- активировать стратегически значимый Замысел;
- отпускать значимый активный Замысел;
- принимать первый существенный маршрут;
- существенно перепланировать результат;
- менять рабочую норму как постоянное правило;
- менять внешнее обязательство.

## 4.4. Рабочая норма

Стартовая рабочая норма текущего пользователя:

**6 часов фактической работы в день.**

Это не вечный закон продукта и не жёстко зашитая константа.

## 4.5. Программа не работает в фоне

Если день / неделя / другой обзор не был обработан, приложение догоняет пропущенное **при следующем запуске**.

Никакая фоновая инфраструктура для этого в MVP не строится.

## 4.6. Google Calendar нужен рано

Календарь является частью реальности, необходимой для корректного `Сейчас`.

Поэтому он появляется до полноценного Исполнятора, а не как поздняя интеграция.

В MVP календарь читается. Собственная календарная сетка не нужна.

## 4.7. Память

Память первой версии должна уметь постепенно прийти к четырём способностям:

1. **хранить**;
2. **находить**;
3. **возвращать нужное вовремя**;
4. **замечать повторения и закономерности**.

## 4.8. Язык интерфейса

Живая карта — русскоязычный продукт.

Весь пользовательский интерфейс (заголовки, кнопки, подписи, placeholder'ы, состояния действий, сообщения об ошибках, пустые состояния, диалоги подтверждения, читаемая история изменений) должен быть на русском языке.

Внутренние технические имена (`Season`, `GoodLifeCondition`, `Intention`, `Action`, `Blocker`, `WorkSession`, MCP, IPC, коды ошибок, `commandType` и т.п.) остаются на английском в коде и не переименовываются ради формулировок — но не должны напрямую отображаться пользователю.

Пользовательский ввод может быть на любом языке — правило касается только продуктового интерфейса, а не содержимого, которое вводит пользователь.

Это постоянное продуктовое решение, а не разовая правка Этапа 2.

## 4.9. Первый запуск: онбординг вместо форм

Финальная Живая карта не должна требовать от нового пользователя вручную заполнять внутренние доменные сущности одну за одной.

Основной первый экран — короткий разговорный онбординг из примерно 5–7 вопросов на обычном человеческом языке (не на языке доменных терминов вроде `GoodLifeCondition`, `OrderedActionPlan`, Stage, Blocker).

Поток:

**пользователь отвечает на онбординг → ИИ интерпретирует ответы → ИИ предлагает черновик структуры Живой карты → пользователь видит, как система его поняла → пользователь правит неточности → пользователь явно подтверждает → только после этого стратегическая структура сохраняется.**

ИИ никогда не создаёт и не меняет стратегическое направление молча — действуют уже зафиксированные правила подтверждения стратегических решений (см. §4.3).

Ручные формы не исчезают. После появления онбординга они остаются как:

- прямое редактирование;
- инспекция;
- исправление;
- fallback / ручное управление;
- разработка/отладка.

Зрелый обычный сценарий использования — это постепенный переход к модели **разговор с ИИ / универсальный захват → ИИ интерпретирует контекст → ИИ предлагает структурное изменение → пользователь подтверждает стратегическое → Живая карта обновляется**, а не ручное заполнение форм как основной способ взаимодействия.

Онбординг не реализуется сейчас. Он относится к ЭТАПУ 8 — ПОЛНАЯ ЖИВАЯ КАРТА, как задел перед 7-дневным реальным тестом (см. §6, Этап 8). Он не создаёт новый номерной этап и не меняет существующий порядок разработки.

# 5. Главные критерии успеха MVP

После семи дней настоящего использования должны одновременно появиться два главных эффекта:

1. **Пользователь реально продвинул главный Замысел.**
2. **Пользователю стало легче жить, потому что меньше нужно держать в голове.**

Дополнительное ограничение:

> приложение само не должно превращаться в новую работу.

# 6. Канонический порядок разработки

## ЭТАП 0. АРХИТЕКТУРА

### Цель

Спроектировать технический фундамент до написания продуктовых функций.

Архитектура должна одновременно:

- быть максимально простой для локального MVP;
- не связывать бизнес-логику с Electron, SQLite, Claude или конкретным UI;
- позволять позже заменить локальное хранение / интерфейс / транспорт MCP без переписывания продуктового ядра;
- не строить облачную инфраструктуру заранее.

### Нужно решить

**Границы приложения:** Electron main process, renderer process, preload / IPC, локальный MCP process, domain layer, application layer, persistence layer, integration layer.

**Границы домена:** Strategy / Season, Intention (Замысел), Stage, Action, Constraint / Blocker, Ordered Action Plan, Calendar Event, Work Session, Capture, Memory, Review, Pattern, Planning Rule. Это не означает реализовать их все на этапе архитектуры.

**Данные:** SQLite как локальный источник истины, Drizzle schema / migrations, repository interfaces, версионирование схемы, backup / restore, audit history там, где она реально нужна, правила конкурентного доступа Electron и MCP к одной БД.

**MCP:** какие данные ИИ может читать, какие инструменты может вызывать, какие действия требуют подтверждения, как проверяются входные данные, как предотвращаются произвольные изменения стратегии, как работает локальный transport, как позже можно заменить локальный transport на remote без изменения домена.

**Расширяемость:** зафиксировать интерфейсы, через которые в будущем можно заменить SQLite → облачная БД/синхронизация, Electron UI → web/mobile, локальный MCP → remote MCP, Google Calendar → другой календарный источник. Не реализовывать эти будущие варианты.

### Не делать

- продуктовые экраны;
- полный data model всех будущих функций;
- облако;
- аккаунты;
- mobile/web;
- сложную абстракцию «на всякий случай».

### Выход этапа

1. `ARCHITECTURE.md`
2. схема процессов и границ;
3. структура каталогов;
4. интерфейсы ключевых слоёв;
5. схема владения данными;
6. модель MCP-полномочий;
7. список архитектурных решений / ADR;
8. минимальный skeleton репозитория только если он нужен для проверки архитектуры.

### Definition of Done

Другой разработчик должен суметь прочитать `ARCHITECTURE.md` и однозначно понять:

- где живёт бизнес-логика;
- где живёт база;
- как UI обращается к домену;
- как MCP обращается к домену;
- что ИИ может и не может менять;
- что можно заменить позже без переписывания продукта.

```text
Текущая версия локальная:
- один пользователь;
- Windows desktop;
- без сервера;
```

## ЭТАП 3. ИИ-МОЗГ ЧЕРЕЗ MCP

### Цель

## ЭТАП 5. ИСПОЛНЯТОР

### Цель

Превратить `Сейчас` из рекомендации в реальную выполненную работу.

### Реализовать

- Начать;
- Пауза;
- Продолжить;
- Готово;
- несколько рабочих сессий в день;
- фактическую длительность;
- связь с действием;
- дневную сумму;
- недельную сумму;
- 6 часов как изменяемую стартовую норму;
- встречи / обед / дорогу не считать рабочим временем;
- после `Готово` обновлять действие и показывать следующий допустимый ход;
- если нужен новый AI-order — явно это показывать.

### Зафиксированное устройство таймера на главном экране

Отдельного экрана таймера нет.

Таймер является частью блока `Сейчас` на главном экране.

В блоке одновременно показываются два разных уровня времени:

1. **Работа за день** — маленьким второстепенным текстом, например `3 ч 15 мин / 6 ч`. Это сумма фактической работы за текущий день относительно изменяемой рабочей нормы.
2. **Работа над текущим действием** — таймер внутри карточки `Сейчас`, например `15:00`. Он показывает суммарное фактическое время работы именно над этим действием, включая несколько отдельных WorkSession.

Если над одним действием пользователь работал 20 минут утром и 35 минут вечером, таймер действия показывает 55 минут, а не только длительность последней непрерывной сессии.

Дневной счётчик увеличивается только за счёт фактических WorkSession. Встречи, обед, дорога и другое нерабочее время в него не входят.

Базовый сценарий:

`Сейчас → Начать → таймер действия идёт → Пауза / Продолжить → Готово → время сохраняется → показывается следующее допустимое действие`.

### Не делать

- геймификацию часов;
- оценку человека по продуктивности;
- искусственные проценты;
- сложную аналитику времени.

### Выход

Через Живую карту можно прожить полный настоящий рабочий день.

### PROMPT ДЛЯ CLAUDE CODE

```text
Реализуй lifecycle текущего действия:

Добавь WorkSession:
- startedAt;
- paused intervals;
- endedAt;

Поддержи несколько сессий в день и фактическую сумму дня/недели.

На главном экране НЕ должно быть отдельного экрана таймера.

Показывай одновременно:
```

## ЭТАП 6. УНИВЕРСАЛЬНЫЙ `+` + ПАМЯТЬ

### Цель

Снять с пользователя обязанность держать важное в голове.

### Реализовать

**Capture:** любой текст через `+` мгновенно сохраняется как сырой оригинал, никогда не теряется из-за недоступности ИИ и имеет состояние обработки.

Если ИИ доступен через MCP, он может разобрать запись. Если нет — запись остаётся сохранённой и ждёт обработки.

ИИ может интерпретировать запись как Замысел, действие, обязательство, решение, факт, наблюдение, память, вопрос или ничего операционного.

**Memory v1:** хранение, поиск, связь памяти с Замыслами/решениями/действиями, чтение релевантной памяти через MCP, возможность ИИ вернуть старое решение в подходящий момент.

Полная автоматическая семантическая магия не нужна, если для неё требуется тяжёлая инфраструктура.

### `+` — основная точка входа пользователя к ИИ (решение владельца, зафиксировано при Gate C Этапа 5)

Реальная проверка Этапа 5 показала продуктовый разрыв: внутри Живой карты нет места, где можно обратиться к ИИ. Когда `Сейчас` приходит в NeedsAIReplan, интерфейс лишь советует «открыть подключённый ИИ», и пользователю приходится уйти из Живой карты, вручную открыть Claude Code и сформулировать запрос там. Для зрелого продукта это неприемлемо.

Поэтому универсальный `+` — не пассивный inbox, а **обычное место, где пользователь пишет Живой карте / её ИИ на естественном языке**. Например:

- «Перестрой порядок, я закончила текущий этап.»
- «Завтра в 15:00 стоматолог.»
- «Добавь идею для видео.»
- «Я поняла, что больше не хочу жертвовать сном.»
- «Что мне сейчас делать?»
- любая сырая мысль, просьба, факт, обязательство или вопрос.

Правило взаимодействия:

**пользователь пишет в `+` → сырой оригинал сохраняется сразу и никогда не теряется → если ИИ доступен, он сразу интерпретирует запись → ИИ может ответить, классифицировать, выполнить безопасное изменение или подготовить Proposal → стратегические/существенные изменения по-прежнему требуют явного подтверждения пользователя (§4.3) → если ИИ недоступен, запись остаётся сохранённой и помеченной как ожидающая обработки.**

Пользователь не обязан знать, чем технически является его ввод (Capture, запрос к ИИ, Action, Memory, Commitment, Question, запрос на изменение маршрута) — система определяет это после сохранения.

**Точка входа из NeedsAIReplan.** Состояние NeedsAIReplan не должно оставлять пользователя только с текстом «открой подключённый ИИ и попроси перестроить маршрут». Интерфейс даёт прямое действие **«Попросить ИИ перестроить»**, которое открывает `+` / ввод для ИИ с уже приложенным или подставленным релевантным контекстом. Продуктовая петля продолжается внутри Живой карты.

**UX ИИ в MVP.** Отдельный большой экран чата сейчас не строится. Предпочтительное взаимодействие: один универсальный ввод на естественном языке (`+`) + ответы и предложения ИИ, показанные в продукте там, где они уместны. Более крупная история разговора / чат добавляется, только если реальное использование докажет необходимость.

**Архитектурная реальность — транспорт.** Сейчас ИИ — внешний host, который подключается к Живой карте через MCP (§4.1, ARCHITECTURE §1). MCP-сервер Живой карты только отвечает на запросы ИИ; сам он не может вызвать ИИ. Эта возможность **сейчас не существует**, и нельзя делать вид, что она есть. До реализации взаимодействия с ИИ на Этапе 6 нужно:

1. изучить фактическую направленность текущего MCP (кто кого вызывает, что умеют выбранные ИИ-host'ы);
2. предложить минимальную жизнеспособную архитектуру, при которой ввод, созданный внутри Живой карты, обрабатывается подключённым ИИ без ручного переключения пользователя в Claude Code;
3. соблюсти требования:
   - сырой capture сохраняется даже при недоступном ИИ;
   - никаких молчаливых потерь;
   - по возможности без жёсткой привязки всего продукта к одному вендору ИИ;
   - стратегические записи — только через Proposal и подтверждение пользователя;
   - никакого доступа к сырой БД и небезопасных возможностей.

Если немедленный вызов ИИ из приложения невозможен в текущей архитектуре «только MCP-сервер» (в том числе с учётом §2/§3: без обязательного собственного ИИ API, и ARCHITECTURE §2: без собственного AI chat и API OpenAI / Anthropic), это выносится **решением владельца в самом начале Этапа 6**, а не скрывается.

**Решение владельца (Owner Gate A Этапа 6, 2026-09-28): вариант B.** Electron main по требованию запускает Claude Code в headless-режиме (`claude -p`, подписка claude.ai пользователя) за заменяемым портом `AiRunner`; запущенный ИИ работает с Живой картой только через тот же локальный MCP и ту же модель полномочий / Proposal. Условия владельца: Живая карта может требовать установленный и залогиненный Claude Code; разбор расходует лимиты подписки; текущее поведение авторизации `claude -p` через claude.ai не считается вечной гарантией; транспорт заменяем за `AiRunner` без изменения продуктовой семантики; при отсутствии/выходе из аккаунта/лимите/офлайне/сбое сырая Capture остаётся сохранённой и ждёт; стратегические изменения — только Proposal + явное подтверждение; большого экрана чата нет; `+` — основной вход к ИИ на естественном языке. **Будущая запись в календарь (уже одобренное правило).** Если в `+` конкретное внешнее событие с датой/временем, ИИ может интерпретировать его как событие календаря. ## ЭТАП 7. РАЗБОРЫ + ОБУЧЕНИЕ НА ПРОЖИТОМ

### Цель

Сделать так, чтобы прожитая жизнь улучшала будущие решения.

### Реализовать

**День:** при следующем запуске после завершившегося дня собрать выполненные действия, рабочие сессии, изменения, события и captures. ИИ выделяет только полезные изменения. Пользователь подтверждает/исправляет.

**Неделя:** реальные результаты, зависшие Замыслы, рабочая ёмкость, важные обязательства, практики, кандидаты в закономерности, предложения изменений.

**Сезон:** что реально изменилось, что оказалось неверным, какие доказательства появились, что воплощено/отпущено, нужен ли новый сезон.

**Год:** проверка траектории относительно дальней карты.

**Закономерности:** факт → повторения → кандидат → подтверждение → правило планирования.

## ЭТАП 9. 7 ДНЕЙ НАСТОЯЩЕЙ ЖИЗНИ + УБОРКА

### Цель

Не добавить функции, а проверить, что продукт действительно меняет жизнь.

### До теста

Довести только необходимое:

- понятная навигация;
- пустые состояния;
- ошибки;
- загрузочные состояния;
- восстановление после сбоя;
- backup;
- минимальная визуальная чистота;
- отсутствие технического мусора на основных путях.

Мобильная адаптация не нужна.

### Семидневный тест

Все семь дней реальный пользователь живёт через систему.

Вести **журнал трения**, а не wishlist.

Записывать:

- где пришлось обходить систему;
- что система забыла;
- где `Сейчас` оказался плохим;
- где Claude не хватало контекста;
- где требовалось слишком много обслуживания;
- где модель данных не совпала с жизнью;
- где действие не привело к реальному продвижению.

### Главные вопросы после 7 дней

1. Продвинулся ли главный Замысел заметно дальше, чем без системы?
2. Стало ли меньше того, что нужно помнить, удерживать и заново решать в голове?
3. Стала ли сама система новой работой?
4. Какие проблемы повторились несколько раз?

Менять продукт только по реальному повторяющемуся трению.

### Выход

MVP, который доказал или опроверг центральную продуктовую гипотезу на реальной жизни.

### PROMPT ДЛЯ CLAUDE CODE

```text

2. повторялось ли это;
3. мешает ли это одному из двух главных критериев:
```

# 8. Правило работы Claude Code в каждом новом контексте

Перед любыми изменениями Claude Code обязан:

1. найти корень репозитория;
2. прочитать `DEVELOPMENT_PLAN.md` целиком;
3. прочитать `ARCHITECTURE.md`, если он уже существует;
4. прочитать актуальный `PRODUCT_SPEC.md`;
5. проверить `git status`;
6. посмотреть последние commits;
7. назвать текущий этап;
8. перечислить, что относится к текущему этапу;
9. отдельно перечислить всё, что относится к будущим этапам и поэтому НЕ будет сделано сейчас;
10. только после этого менять код.

После работы Claude обязан:

1. перечислить изменённые файлы;
2. объяснить, какое требование текущего этапа реализовано;
3. показать тесты;
4. назвать незакрытые пункты Definition of Done;
5. не объявлять этап завершённым, если хотя бы один обязательный пункт не проверен.

Claude Code не начинает следующий этап самостоятельно.
