# Этап 6 — живая валидация универсального `+` и Памяти

Фиксирует реальную проверку `+`, Capture-очереди и Памяти v1 в реальном приложении на реальных данных
владельца, а не только тесты. Модель и решения — ADR-0007. Секреты, приватный iCal-адрес, пути к данным и
дословный текст личных воспоминаний владельца здесь намеренно не приводятся.

## Gate A — решение владельца (транспорт)

Вариант B: Electron main по требованию запускает Claude Code headless (`claude -p`) за портом `AiRunner`;
ИИ работает с Живой картой только через локальный MCP. Условия владельца перечислены в ADR-0007.

## Gate B — корректность и одобрение

Живая проверка вскрыла: Claude Code ждёт MCP только ~2,5 с перед `init`; более медленный старт помечается
`pending`, хотя инструменты работают. Старый парсер считал это `mcp_failed`, даже когда результат был
валиден. Исправлено:

- парсер принимает `pending`;
- очередь продолжает разбор следующих Capture после сбоя одной записи;
- новая колонка `captures.proposal_id` (миграция 0012, с backfill) и `LIVING_MAP_CAPTURE_ID` в окружении
  MCP-потомка сделали повтор одной записи идемпотентным (повтор не создаёт второй Proposal).

Владелец одобрил Gate B. Добавлена правка Memory v1: экран «Память», `memory.forget` — жёсткое удаление,
доступное только пользователю из UI, недоступное ИИ/MCP.

## Независимый review

0 HIGH, 4 MEDIUM — все исправлены до Gate C; относящиеся к делу LOW-правки применены. Итог зафиксирован в
памяти сессии; подробный построчный список замечаний не переносился в отдельный файл репозитория.

## Gate C — реальное использование

Проверено напрямую через `mcp__living-map__*` (те же данные, что видит desktop) — read-only, без изменения
реальных данных.

### `+` и Capture

8 реальных Capture владельца, все `state: processed`, `rawText` не тронут:

| Тип ввода | Пример результата |
|---|---|
| Вопрос | «Что мне сейчас делать?» → `kind: answer`, ответ по текущему `Сейчас`/Proposal |
| Вопрос к памяти | «Какую идею я хотела использовать в видео про дисциплину?» → `kind: answer`, ответ из Памяти |
| Факт/идея | «Добавь идею снять видео про стиль дисциплины» → `kind: memory`, сохранена |
| Обязательство с датой | «Завтра в 10.40 барабаны до 12.10» → `kind: no_operation` при повторе (уже помнится), запись в системный календарь честно названа недоступной |
| Запрос перестройки | «Перестрой текущий порядок действий.» → `kind: proposal`, создан и принят Proposal |
| Запрос перестройки (повтор) | «Перестрой порядок, я закончила Исполнятор» — 2 попытки, `attempts: 2`, **один** Proposal (`31348fc0`), второй не создан |

Все 4 типа из Definition of Done действия «Проверить полный цикл «+» и памяти» (вопрос, факт/идея, просьба
перестроить маршрут, событие) реально прогнаны.

### Память

- Сохранено и **доступно** через `search_memory`: идея для видео («стиль дисциплины»), обязательство про
  барабаны 30 сентября.
- **Забыто** владельцем через реальный UI (`memory.forget`, actor `user-ui`): решение про сон/работу
  (`d7e729e1`) и идея «свобода появляется внутри выбранной рамки» (`f23e2818`) — оба **отсутствуют** в
  `search_memory` (пустой запрос вернул только 2 живые записи, не 4).
- Исходные Capture для обеих забытых записей существуют без изменений (`rawText` совпадает с оригиналом
  ввода); их отображаемый результат честно говорит «Этого больше нет в памяти» вместо того, чтобы показать
  забытое содержимое повторно — согласованно с тем, что `memory.forget` — необратимое удаление, а не просто
  скрытие в выдаче.
- ИИ использовал реальное текущее состояние Живой карты (реальные Этапы/Proposal/`Сейчас`), а не выдумывал
  его — видно по точному соответствию текста ответов и rationale Proposal реальным Stage id/title.

### Capture-надёжность

- Сырой Capture закоммичен до вызова ИИ во всех 8 записях (`capture.create` всегда предшествует
  `capture.processed` в `recentHistory`, разные `stateRevision`).
- Триггер `captures_raw_text_immutable` (BEFORE UPDATE OF raw_text) подтверждён в
  `packages/persistence-sqlite/drizzle/0011_capture_raw_text_immutable.sql`.
- Повтор/сбой не задвоил Capture → Proposal: `a93ee71d` (2 попытки) и `bbda3811` (1 попытка) — по одному
  Proposal каждая, `captures.proposal_id` совпадает с фактически принятым/протухшим Proposal.
- Ни одна запись не осталась «зависшей» в `pending`/`processing`: все 8 — `processed`; восстановление
  очереди при старте (`app.commands.recoverCaptures`, вызывается при launch в
  `apps/desktop/src/main/ai/capture-processor.ts`) переводит `processing → pending` и годный `failed →
  pending`, что согласуется с отсутствием зависших записей в реальной БД.
- Успешные Proposal-порождающие Capture не помечены `failed` — обе (`a93ee71d`, `bbda3811`) — `processed`.

### Proposal / маршрут

- Первый Proposal по запросу владельца перестроить (`31348fc0`) стал `stale` (`resolvedBy: user-ui`,
  `resolvedAt: 2026-09-29T12:40:36Z`) после того, как реальность разошлась (владелец вручную переключил
  текущий Этап) — не применён, дубликат не создан.
- Второй, актуальный Proposal (`9eead511`) — `status: accepted`, `resolvedBy: user-ui`,
  `resolvedAt: 2026-09-29T13:43:50Z`. Его `payload.orderedActionIds` дословно совпадает с текущим
  `orderedActionPlan.orderedActionIds` (v3, `sourceRevision: 113`).
- Текущий Этап («Добавить универсальный «+» и память»), `OrderedActionPlan` и `Сейчас`
  (`d477abf0-fb62-4fc9-8a5b-74cca292c38e`, reason `first-in-plan`, `needsAiReplan: false`) отражают именно
  это решение владельца.
- `stateRevision` монотонно растёт 1→117 без разрывов в прочитанной истории; владелец подтвердил, что
  состояние пережило реальный перезапуск приложения.

## Проверено тестами и живым read-only чтением, не полным независимым повтором ревью

Раздел 4 задачи прямо запрещает повторный большой review без нового бага от Gate C — новых корректностных
багов Gate C не вскрыл, поэтому review не повторялся; отчёт выше — это read-only проверка реальных данных
через `mcp__living-map__*`, а не код-ревью.

## Автоматическая проверка (финальный прогон)

Biome (0 замечаний, 125 файлов), typecheck всех пакетов, **Vitest 293/293**, Electron build (main/preload/
renderer/mcp) и **Playwright e2e 8/8** (включая все 4 новых сценария Этапа 6 — сохранение и восстановление
`+`, недоступный ИИ + «Повторить», NeedsAIReplan → «Попросить ИИ перестроить», экран «Память» с поиском и
забыванием) — все зелёные на финальном diff.

## Известные ограничения (LOW, приняты)

- Забытая память — необратимое удаление на уровне UI (не MCP); отменить «забывание» нельзя.
- `CalendarWriter` не реализован — обязательства с датой честно остаются только в Памяти, ИИ прямо говорит,
  что в Google Календарь запись не делает.
- Поиск по памяти — детерминированный локальный (совпадение по началу слова + свежесть), без векторов и
  внешней семантики — по замыслу Этапа 6, не баг.
- Построчный список 4 MEDIUM независимого review не сохранён отдельным файлом репозитория — только
  агрегированный итог (0 HIGH, 4 MEDIUM, все исправлены) в памяти сессии.
