## Найденный и исправленный баг: разворачивание recurrence

При живой проверке с реальным повторяющимся событием (ежедневное расписание класса,
`packages/integrations-ical-calendar/src/ical-provider.ts`) обнаружилось: цикл разворачивания серии
всегда начинал итерацию с истинного `DTSTART` события. Для давно идущей ежедневной серии это
исчерпывало весь бюджет `MAX_OCCURRENCES_PER_SERIES` на прогулку от старого `DTSTART` и никогда не
доходило до вхождений рядом с `now` — серия тихо пропадала из снимка целиком.

**Исправление:** итератор теперь стартует не раньше целых суток до `now` (сохраняя исходные
час/минуту/таймзону `DTSTART`, поскольку `ICAL.RecurIterator` берёт время суток у переданного seed),
если это позже самого `DTSTART`; для серии, чей `DTSTART` ещё в будущем, итерация по-прежнему идёт от
настоящего `DTSTART` — назад не откатывается. См. комментарий в коде и
`packages/integrations-ical-calendar/test/ical-provider.test.ts`.

## Независимый review

Полный diff Этапа 4 прошёл отдельный независимый code review (агент `code-reviewer`, вне контекста
реализации), включая реальный запуск `createIcalCalendarProvider` через `ical.js` с рукописными
фидами — не только чтение кода.

**Найдено и исправлено:**

- **[HIGH] Разворачивание recurrence было некорректным для любой серии, начавшейся в прошлом.**
  Оптимизация «промотать итератор вперёд до `now`» подменяла seed итератора вместо истинного
  `DTSTART`, из-за чего `ical.js` пересчитывал `COUNT`, `INTERVAL` и отсутствующие `BYDAY`/
  `BYMONTHDAY`/`BYMONTH` относительно seed, а не `DTSTART` — уже закончившиеся серии с `COUNT`
  «воскресали», ритм `INTERVAL>1` съезжал, а правила без явного `BY*` переезжали на день/неделю/месяц
  seed-даты. Подтверждено запуском реального `ical.js` 2.2.1. **Исправление:** итератор всегда
  стартует от настоящего `DTSTART`; вместо промотки seed добавлена дешёвая проверка (по
  приблизительному концу occurrence через `base.duration`) перед дорогим `getOccurrenceDetails`,
  бюджет `MAX_OCCURRENCES_PER_SERIES` поднят до 50 000. Добавлено 5 регрессионных тестов
  (закончившаяся `COUNT`-серия, `INTERVAL=2`, недельная/месячная/годовая без `BY*`) —
  `packages/integrations-ical-calendar/test/ical-provider.test.ts`.
- **[MEDIUM] «Обновлён только что» и список «Ближайшие события» не устаревали, пока приложение
  открыто.** Экран не перерисовывался сам по себе — только по смене состояния. Добавлен тик раз в 60с
  (`useClockTick`, `now-screen.tsx`) и явное предупреждение об устаревании данных календаря старше 3
  часов (`calendar-stale`), как того требует ARCHITECTURE §32.
- **[LOW] Неудачное «Подключить» всё равно очищало вставленную ссылку**, хотя подключение
  провалилось (`connected: false`/`lastError` заполнен) — комментарий в коде обещал очистку только
  «после успешного подключения», а очищал при любом `ok: true`. Исправлено: очистка теперь требует
  `connected && !lastError`.
- **[LOW] Автоматическое обновление календаря при запуске приложения записывалось в историю от
  имени `user-ui`**, хотя пользователь его не инициировал. `refresh()` оркестратора теперь принимает
  явный `actor` (ARCHITECTURE §19); запуск передаёт `"system"`.
- **[LOW-MEDIUM] `calendar.save` (рутинное событие на каждом запуске/обновлении) засорял
  `recentHistory` для ИИ (лимит 30) и историю в UI (лимит 20).** Не «существенное изменение» по
  смыслу ARCHITECTURE §20 — исключено из `changeLog.listRecent` на уровне персистентности; сама
  запись в таблице сохраняется (нужна для `state_revision`), но не попадает в выдачу истории.
- Уточнён комментарий `.gitignore` (упоминал устаревшие «Google Calendar OAuth tokens»).

**Рассмотрено и сознательно не реализовано в Этапе 4 (задокументировано, не блокирует):**

- **Календарь пока не влияет на выбор `Сейчас`.** `CurrentActionSelector` проверяет окно до
  жёсткого события только когда у Action есть `estimatedDurationMinutes` — а ни один реальный Action
  в текущей модели данных длительность не хранит (см. комментарий в
  `packages/domain/src/current-action.ts`: «never invent one to make filtering work»). Это осознанное
  ограничение объёма Этапа 4, а не баг: оценка длительности действий — отдельное продуктовое решение
  за пределами календарной интеграции.
- **Узкое окно гонки** между одновременными `connect`/`refresh`/`disconnect` (например, обновление
  при запуске ещё не завершилось, когда пользователь уже вставил новую ссылку) — маловероятно для
  одного локального пользователя, кликающего вручную; самоисправляется на следующем обновлении.

Независимый review также подтвердил чистым: точность `CurrentActionSelector` (нет переранжирования),
