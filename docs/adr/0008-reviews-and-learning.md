# ADR-0008 — Разборы и обучение на прожитом: Review, AI review job, Pattern → PlanningRule

**Статус:** принято (Этап 7, черновик до Gate C)
**Уточняет:** ARCHITECTURE.md §36 (Разборы без background service); ADR-0007 (`AiRunner`, Capture queue)

## Контекст

Этап 7 должен превращать прожитую жизнь в лучшие будущие решения: `lived facts → useful finding →
repeated evidence → Pattern candidate → owner confirmation → active PlanningRule`. Никакого фонового
процесса; ИИ анализирует только факты, уже присутствующие в системе.

## Решения

### 1. Один `Review` на все четыре вида

Таблица `reviews`: `id, type (daily|weekly|seasonal|yearly), periodStart, periodEnd, timeZone, status
(needs_ai|processing|ready|no_useful_change|failed), attempts, lastError, createdAt, updatedAt`.
Уникальный индекс `(type, periodStart, periodEnd)` — дубликат периода невозможен на уровне БД.

Daily/weekly/yearly — календарные периоды, вычисляются чистыми доменными функциями
(`dueDailyPeriods`/`dueWeeklyPeriods`/`dueYearlyPeriods`, `packages/domain/src/review.ts`) от `lastPeriodEnd`
(курсор — `periodEnd` последнего `Review` этого типа) до текущего момента; текущий, ещё не завершённый
период никогда не due. Первый запуск после появления Этапа 7 не создаёт годы бэклога: если у типа ещё
нет ни одного `Review`, due — только один, самый последний завершённый период.

Seasonal — не календарный: период — это закрытый интервал между двумя последовательными
`season.create`/`season.updateFocus` записями `change_log` (Season — singleton без собственной истории
фокуса, поэтому старый текст фокуса для давно закрытого интервала недоступен и не подделывается;
доступны только факты, случившиеся *внутри* интервала). `dueSeasonalPeriods`
(`packages/application/src/review-evidence.ts`) перебирает все такие интервалы и создаёт `Review` только
для тех, где ещё нет строки (проверка по уникальному индексу).

**Выбранная граница (bounded catch-up, §10):** `scheduleDueReviews` создаёт до 60 daily / 26 weekly / 10
seasonal / 5 yearly `Review`-строк за один запуск — это лишь дешёвые INSERT'ы (без обращения к ИИ),
поэтому не блокируют старт. Остаток (если курсор ещё дальше в прошлом) подхватывается следующим
запуском — период никогда не теряется, просто создание строк растягивается на несколько запусков.
Дорогая часть (разбор ИИ) уже ограничена одним активным запросом за раз (см. §4).

### 2. Evidence pack — закрытое множество, не MCP

В отличие от Capture (Этап 6), запуск ИИ для Review **не получает MCP-сервер вовсе**: единственный
источник фактов — заранее собранный `ReviewEvidencePack` (`packages/application/src/review-evidence.ts`),
переданный только через stdin. `evidenceRefs`, которые ИИ вернёт, валидируются как принадлежность
конечному множеству id из этого pack'а (`packages/application/src/application.ts`, `finishReview`) —
не доверие к придуманному ИИ id, а точная проверка подмножества. Это одновременно проще и надёжнее
инструмента чтения: ИИ физически не может позвать что-то ещё, а «выдуманная» ссылка отклоняется
детерминированно, без обращения к БД заново.

Evidence собирается из уже существующих порт-методов, расширенных для периодов (`listCompletedBetween`,
`listResolvedBetween`, `listCreatedBetween`, `listBetween`/`listByCommandTypes` на `changeLog`) —
завершённые действия, рабочие интервалы, Capture, Memory, разрешённые Proposal и значимые записи
`change_log` периода, за вычетом уже покрытых отдельно и чисто технических типов.

### 3. AI review job через тот же `AiRunner`

`AiRunner.processReview(evidence, signal)` — второй вид задачи через тот же заменяемый транспорт
(`ClaudeCodeCliAiRunner`, `apps/desktop/src/main/ai/claude-code-cli.ts`), не второй транспорт. Общая
инфраструктура запуска процесса (`runJob`) переиспользована; отличается только системный промпт,
JSON-схема результата (`ReviewAiResultSchema`) и — единственно важное — **отсутствие** `--mcp-config`/
`--allowedTools` (`buildReviewClaudeArgs`). `interpretCliOutput`/`interpretReviewCliOutput` разделяют
общий разбор `stream-json`, но проверка статуса MCP-сервера пропускается для Review (`requireMcp: false`),
потому что сервера нет и не должно быть.

Результат — `{ kind: "no_useful_change" } | { kind: "findings", findings: ReviewFindingDraft[] }`
(`packages/contracts/src/review.ts`). Каждая находка: `text` (по-русски, что учесть дальше — не пересказ),
`evidenceRefs` (⊆ pack), `suggestion` (опционально — предложение стратегического изменения текстом,
никогда не применяется автоматически: пользователь сам поднимает его через `+`), `patternKey` (короткий
слаг темы, если похоже на повторение).

### 4. Обработка — та же очередь, что и Capture

`ReviewProcessor` (`apps/desktop/src/main/ai/review-processor.ts`) — почти дословная копия
`CaptureProcessor`: `claimNextReview` (`needs_ai → processing`, атомарно) → `processReview` вне
транзакции → `finishReview` (одна транзакция: валидация evidence, запись находок, одна ревизия). Один
активный запрос ИИ одновременно (single-flight), как и для Capture — не второй фреймворк очереди.
`start()` при запуске: `scheduleDueReviews` → `recoverReviews` (интерпретирующий `processing`/исчерпанный
`failed` в `needs_ai`, тот же паттерн, что `recoverCaptures`) → `kick()`.

`finishReview` — fail-closed: некорректный JSON, любая несуществующая `evidenceRef` или невалидная
находка (по доменным ограничениям) переводят **весь** результат в `failed` — не частичная запись
находок. Это единственная защита от «правдоподобного, но частично выдуманного» ответа.

### 5. Pattern pipeline — по `patternKey`, не по семантике

`fact evidence → repeated accepted evidence → Pattern candidate` реализовано детерминированно, без
эмбеддингов: `maybeSurfacePatternCandidate` (`application.ts`) вызывается после `acceptReviewFinding`/
`correctReviewFinding` (никогда после `reject`) и ищет все `accepted`/`corrected` находки с тем же
`patternKey`. Кандидат создаётся, только если находки принадлежат **≥2 различным `Review`**
(`MIN_PATTERN_EVIDENCE`, `packages/domain/src/pattern.ts`) — не просто двум находкам одного разбора
(проверено тестом «a single episode never becomes a candidate»). `Pattern.evidenceFindingIds` хранится
как JSON-массив id находок (тот же приём, что `ordered_action_plans.ordered_action_ids`).

Дубликаты/воскрешение отклонённого предотвращаются поиском по `patternKey` (`findByKey`, не более одной
неотклонённой строки на ключ) плюс проверкой подмножества: у `rejected`-записи новый набор evidence
должен выходить за пределы уже отклонённого набора, иначе кандидат повторно не создаётся. Новая
находка, расширяющая множество, законно создаёт новый кандидат (не то же самое отклонённое).

### 6. PlanningRule — активация только пользователем

`confirmPattern` (`user-ui`/`system` only; `mcp-ai` не имеет policy-записи вообще ни для одной команды
Этапа 7 — структурально не может ни обработать Review, ни подтвердить Pattern, ни включить правило)
атомарно переводит `Pattern` в `confirmed` **и** создаёт активный `PlanningRule` одной транзакцией.
`PlanningRule.text` — обычный текст, без интерпретации локальным кодом (никакого DSL, ARCHITECTURE §48).

Видимость ИИ: `get_living_map_context` (MCP) теперь включает `activePlanningRules` в
`PlanningContextDto`, с пояснением в `PLANNING_MEANINGS` — «реальный контекст, никогда не правило,
которое ты применяешь механически». Отключённое правило (`deactivatePlanningRule`) немедленно пропадает
из этого списка (не hard-coded фильтр в MCP — просто `planningRules.listActive()`).

## Независимое ревью (Этап 7, до Gate B)

Отдельный проход `code-reviewer`: 3 HIGH, 10 MEDIUM, 8 LOW. Все HIGH и большинство MEDIUM/дешёвых LOW
исправлены до Gate B; итоговый тест-сьют — 343 unit/integration (было 330) + 11/11 E2E (было 8/8).

**Исправлено:**

- **H1 — периоды разбора пересекаются (день внутри недели/сезона/года), и один и тот же факт из двух
  разных Review засчитывался как «два независимых эпизода».** `maybeSurfacePatternCandidate` теперь
  дополнительно требует, чтобы объединение `evidenceRefs` всех совпадающих находок содержало ≥2
  *различных* id, а не просто ≥2 разных `reviewId` (`application.ts`).
- **H2 — при обрезке evidence-пакета (200 фактов) самое важное для weekly/seasonal («что реально
  изменилось») отбрасывалось первым, потому что `change_log` шёл последней категорией.** Порядок
  категорий изменён (`change_log` теперь первый); для weekly/seasonal/yearly рабочие интервалы
  агрегируются в одну запись на действие вместо записи на интервал; `ReviewEvidencePack` получил
  `truncated`, о чём явно сообщается ИИ в сообщении (`review-evidence.ts`, `claude-code-cli.ts`).
- **H3 — задача ИИ без состояния и без MCP не могла узнать, какой `patternKey` уже используется, поэтому
  два независимых запуска почти никогда не изобретали одинаковый слаг — повторение фактически не
  обнаруживалось.** Evidence pack теперь несёт `knownPatternThemes` (до 30 существующих тем с примером
  текста, `listDistinctPatternThemes`); системный промпт явно требует переиспользовать точный слаг
  известной темы, если она подходит.
- **M1 — смена системного часового пояса могла переоткрыть/задвоить уже разобранный период**, так как
  `lastPeriodEnd` переинтерпретировался в НОВОМ поясе. Курсор теперь читает `lastPeriodEnd` в поясе,
  которым он был *записан* (`LastReviewPeriod`, `packages/domain/src/review.ts`), а не в текущем.
- **M2 — задача Review не передавала `--strict-mcp-config`, поэтому пользовательские MCP-серверы
  (`~/.claude.json`, project `.mcp.json`) могли неожиданно загрузиться** несмотря на намерение «без MCP
  вообще». `buildReviewClaudeArgs` теперь передаёт `--strict-mcp-config` с пустым списком серверов.
- **M3 — собственная техническая отчётность Этапа 7 (`review.*`, `reviewFinding.*`, `pattern.*`,
  `planningRule.*`, `work.start/resume/pause/recover`) не исключалась из evidence и из
  пользовательской истории**, создавая риск self-referential «доказательств» и заслоняя реальную
  историю в контексте ИИ Capture. Расширены `REDUNDANT_OR_TECHNICAL_COMMANDS` (`review-evidence.ts`) и
  `UNLISTED_COMMANDS` (`store.ts`).
- **M4 — повторное совпадающее свидетельство создавало ВТОРОГО кандидата/правило для той же темы**,
  включая после подтверждения. `Pattern` теперь хранит `patternKey`; на тему — не более одной
  неотклонённой строки: существующий `candidate` растёт (`growPatternCandidate`), `confirmed` не
  трогается, у `rejected` требуется доказательство за пределами уже отклонённого набора.
- **M5 — исправление пользователя («на самом деле дело не в этом») не отменяло привязку ИИ к теме**,
  поэтому опровергнутая находка продолжала засчitываться как свидетельство. `correctFinding` теперь
  сбрасывает `patternKey` в `null`.
- **M6 (частично) — пустой evidence-пакет всё равно вызывал ИИ**, соревнуясь с Capture за лимиты подписки
  после долгого перерыва. `ReviewProcessor` теперь завершает такой Review как `no_useful_change` без
  вызова ИИ. Отдельно: Capture и Review были независимыми single-flight очередями и могли звать ИИ
  одновременно, нарушая инвариант ADR-0007 «одна задача ИИ одновременно» — `serializeAiRunner`
  (`apps/desktop/src/main/ai/serialize.ts`) сериализует оба вида задач через общий `AiRunner`.
- **M9 — список «Разборов» показывал 30 записей, а бейдж считал до 200**, поэтому старый непрочитанный
  Review мог остаться недостижимым при этом продолжая считаться в бейдже. UI теперь запрашивает те же
  200.
- Дешёвые LOW: сырые коды ошибок (`malformed`, `not_installed`) в UI заменены на русский текст
  (переиспользован `FAILURE_TEXT` из `plus.tsx`); период недели/сезона/года отображался как включающий
  `periodEnd`, хотя граница исключающая (`formatPeriod` теперь показывает последний включённый день, в
  поясе самого Review, а не поясе рендерера); ошибки `scheduleDueReviews`/`recoverReviews` в
  `ReviewProcessor.start()` больше не проглатываются молча.

**Сознательно отложено** (задокументированный остаточный риск, не блокирует Gate B):

- **M7 — evidence для завершения действия берётся из `completedAt`, а не из записи `change_log`
  `action.complete`.** Переоткрытие/повторное завершение действия до разбора периода может убрать факт
  из evidence того периода. Отдельно: пакет пересобирается заново при `finishReview` (а не берётся из
  снимка на момент `claim`), поэтому реальное изменение данных между claim и finish может превратить
  корректный ответ ИИ в `malformed`. Осознанный компромисс: пересборка = проверка по актуальной правде,
  а не по устаревшему снимку; истинное исправление («источник фактов — сам change_log») отложено.
- **M8 (частично) — недельный/сезонный разбор не получает структурированных «зависших Замыслов» и
  «рабочей ёмкости против нормы»** — только текстовую разницу промпта по типу и перенесённые темы
  `patternKey`. Полноценное агрегированное evidence для этого — отдельная задача.
- LOW: часовые пояса со сменой DST ровно в полночь (например Santiago) могут сдвинуть границу на час —
  самовосстанавливается на следующий проход через `existsForPeriod`, не корневая причина Этапа 7.
  Забытая память (`memory.forget`) не влияет на связанные Capture — их сырой текст по-прежнему может
  попасть в evidence будущего разбора (согласованное поведение Этапа 6, но новый путь появления в
  Этапе 7 — решение владельца, если станет проблемой). Скачок часов вперёд может надолго остановить
  daily/weekly, пока `now` не «догонит» — `maxPeriods` не даёт этому заблокировать запуск, но не чинит
  сам разрыв.

## Отложено сознательно (изначально)

- ReviewFinding → Proposal напрямую: `suggestion` — только текст для пользователя; ревью-задача вообще
  не имеет доступа к MCP и не может создать Proposal сама. Если это станет узким местом на практике —
  отдельное решение владельца.
- Ручное редактирование текста Pattern-кандидата перед подтверждением (сейчас только confirm/reject).
- Семантическое сопоставление находок без `patternKey` (сейчас точное совпадение слага, заданного ИИ,
  подкреплённое списком уже известных тем в evidence pack — см. H3 выше).
- YearlyReview: полноценное сравнение с дальней картой невозможно до Этапа 8 (`LifeDirection`/горизонты
  не существуют) — год анализируется той же evidence-моделью, что и остальные типы, без придуманной
  траектории (системный промпт явно это запрещает).

## Второй независимый проход (pre-Gate-B verification, до Gate B)

Отдельный fresh-context проход `code-reviewer`, специально проверивший H1/M1/M3 против реального кода, а
не только против текста ADR выше. Нашёл, что обе защиты от переучёта были неполными; оба исправлены до
Gate B с новыми регрессионными тестами. Итоговый тест-сьют — 346 unit/integration (было 343) + 11/11 E2E
(без изменений).

**Исправлено:**

- **H1 (доработка) — старая проверка «≥2 разных reviewId» + «≥2 разных evidenceRef в объединении» всё
  ещё пропускала переучёт: два факта одного дня, процитированные ОБОИМИ (daily и weekly) находками без
  изменений, давали 2 разных reviewId и 2 разных ref в объединении, хотя ни один Review не давал ничего
  независимого от другого.** `maybeSurfacePatternCandidate` (`application.ts`) теперь группирует refs по
  `reviewId` и требует ≥2 Review, каждый из которых цитирует хотя бы один ref, не процитированный никаким
  ДРУГИМ Review в группе — настоящий независимый эпизод, а не повторная цитата чужого. Регрессионный тест:
  `review.test.ts` «2 distinct reviewIds and 2 distinct refs are still not enough...».
- **LOW (найдено этим проходом) — воскрешение отклонённой темы проверялось на уровне finding-id, а не
  review-id: вторая находка того же периода (например ранее оставленная «proposed»), впоследствии
  принятая, засчитывалась как «новое доказательство», хотя её Review уже был учтён в отклонённом наборе.**
  Тот же `independentReviewIds` теперь используется и здесь: воскрешение требует хотя бы одного Review за
  пределами набора Review'ов уже отклонённого паттерна. Регрессионный тест: «a rejected theme resurfaces
  only once a genuinely new Review contributes evidence...».
- **M1 (доработка) — фикс работал только в одном направлении смены пояса.** `duePeriods`
  (`packages/domain/src/review.ts`) корректно читал `last.periodEnd` в СТАРОМ поясе, чтобы получить
  гражданскую дату курсора, но затем всё равно превращал эту дату обратно в момент через
  `toInstant(cursor, timeZone)` — то есть полночь этой же календарной даты, но уже в НОВОМ поясе. Если
  новый пояс впереди старого (например NY→Tokyo), это давало более РАННИЙ момент, чем настоящий конец
  предыдущего периода — реальное пересечение (переоткрытие уже разобранного отрезка), не поймано
  единственным существовавшим тестом (он проверял только направление «назад», где это даёт разрыв, а не
  пересечение). Теперь первый возобновлённый `periodStart` — это `last.periodEnd` буквально, без
  пересчёта; каждая следующая граница периода в рамках одного launch-catch-up тоже сцепляется с концом
  предыдущей, а не пересчитывается заново. Регрессионный тест (domain): «...(eastward: zone moves
  ahead)», проверено против кода до фикса (падал бы с пересечением).
- **M3 (доработка) — из `UNLISTED_COMMANDS` (`persistence-sqlite/src/store.ts`) исключены были только
  `review.claim/failed/recover`; `review.due`, `review.processed` и `review.findingCreated` всё ещё
  засоряли и пользовательскую историю, и `recentHistory` в MCP planning context** (catch-up на одном
  запуске может создать/завершить до 101 due-периода). Добавлены в исключение — `review.retry`
  сознательно оставлен видимым: это собственное осознанное действие пользователя («Повторить»), как и
  `capture.retry` рядом с ним.

**Задокументировано, не исправлено (требует владельческого решения об архитектуре evidence-id, не просто
баг-фикса):**

- **H2 (не исправлено) — один и тот же реальный факт получает РАЗНЫЕ evidence-id в зависимости от типа
  Review или от того, как он попал в систему, поэтому независимость по «непересекающимся ref» (H1-фикс
  выше) можно обойти без единого совпадающего id.** Два конкретных пути в `review-evidence.ts`:
  1. Рабочий интервал: daily цитирует `worksession:<intervalId>`; weekly/seasonal/yearly агрегируют тот же
     интервал под `worktotal:<actionId>:<periodStart>` — разные строки для одной и той же работы.
  2. Одна запись `+`: может одновременно попасть в evidence как `capture:<id>` (сырой текст) и, если ИИ
     создал из неё Memory, как `memory:<id>` — тоже разные строки для одного жизненного события.

  H1-фикс проверяет непересечение СТРОК-id, а не совпадение факта, поэтому две находки, честно цитирующие
  один и тот же факт под разными id-схемами, всё ещё пройдут как «независимые». Настоящее исправление
  требует канонической идентичности факта (например: агрегат несёт список исходных interval-id; Memory
  несёт id исходной Capture) — это архитектурное решение о форме evidence pack, не точечный баг-фикс, и
  не делается без отдельного решения владельца (в духе уже принятого M7 выше — «источник фактов — сам
  change_log» тоже сознательно отложен). Отслеживается как неразрешённый HIGH до отдельного решения.
- **M2 (не исправлено) — каждое `season.updateFocus` закрывает «сезон» для `dueSeasonalPeriods`,** даже
  правка формулировки; сезонный разбор появляется только ПОСЛЕ уже случившейся смены, поэтому вопрос
  «нужен ли новый сезон» структурно не может быть задан заранее. Требует продуктового решения (минимальная
  длина сезона? отдельно различать «правку» от «настоящей смены»?), не технического фикса — не в рамках
  этого прохода.
- **M4 (не исправлено) — пользователь подтверждает находку/паттерн, не видя текстов процитированных
  фактов** (`reviews.tsx`): карточка кандидата показывает только «Основано на N находках из разных
  разборов», без самих текстов evidence. Дух ARCHITECTURE §23 (прозрачность Proposal) к Pattern не
  применён буквально (Pattern не Proposal), но тот же принцип напрашивается. UI-доработка, не коррекция
  инварианта — решение владельца.
- **M5 (пересмотрено, не изменено) — «Исправить» всегда сбрасывает `patternKey` в null, даже для мелкой
  правки формулировки**, не только смысловой. Это осознанное решение M5 (см. выше), а не забытый случай;
  альтернатива (различать «правку слов» от «правки сути») потребовала бы дополнительного UI-сигнала от
  пользователя — не делается без отдельного решения владельца.
- **M6 (не исправлено) — отключение `PlanningRule` не имеет подтверждения и не имеет обратного пути**
  (`reviews.tsx`): один клик «Отключить» без «вы уверены», и активировать заново нельзя — только новый
  цикл evidence → кандидат → подтверждение с нуля. Продуктовый вопрос (нужна ли «реактивация» в этом
  этапе), не баг — решение владельца.
- **LOW — canon-примечание (CLAUDE.md §1): ARCHITECTURE.md §26 перечисляет «confirmed planning rules,
  когда они появятся» как один из входов `CurrentActionSelector`.** Фактическое решение этого этапа (§6
  выше) — `PlanningRule` НИКОГДА не читается `CurrentActionSelector`/`current-action.ts`, а передаётся ИИ
  только как обычный текст через `get_living_map_context`, намеренно во избежание второго планировщика.
  Это уточнение, не противоречие по существу (§26 говорит «когда появятся» — не обязывает именно
  локальный детерминированный вход), но текст §26 formally предполагал прямое участие в селекторе.
  Зафиксировано здесь как явное уточнение решения, а не молчаливое отклонение от канона; сам
  ARCHITECTURE.md не менялся — решение об обновлении его текста остаётся за пользователем.

## Третий проход (закрытие перед Gate B): каноническая идентичность факта, границы сезона, видимая evidence, семантика правки

Отдельный проход, специально нацеленный на инвариант «один прожитый эпизод не должен становиться
Pattern только потому, что представлен несколькими формами». Все четыре пункта, ранее
задокументированные выше как нерешённые (H2, M2, M4, M5), закрыты; M6 сознательно не расширялся
(остаётся нерешённым по продуктовому решению владельца, не баг).

### H2 — каноническая идентичность underlying-факта

Инвариант: **разные evidence-ссылки на один и тот же прожитый факт не должны давать независимое
повторение.** Строковое неравенство `evidenceRefs` (H1-фикс) не доказывает, что факты разные —
только что их *представления* разные.

Решение — не семантическое сопоставление и не generic event sourcing (запрещено §2/48), а точечная
provenance-модель поверх уже существующих данных:

- `ReviewEvidenceItem` (`packages/application/src/ports.ts`) получил `factIds: readonly string[]` —
  канонические id underlying-факта(ов), которые этот evidence-item представляет. Никогда не
  показывается ИИ (`buildReviewUserMessage` берёт только `id`/`text`).
- `buildReviewEvidence` (`review-evidence.ts`) заполняет `factIds` из уже существующих связей:
  - первичный факт (`action:`, `proposal:`, `capture:`, `changelog:`) — `factIds` = [собственный id];
  - рабочий интервал: и одиночный дневной `worksession:<intervalId>`, и агрегированный
    `worktotal:<actionId>:<periodStart>` несут `factIds = [interval:<id>, ...]` — те же интервалы,
    просто под другим именем при агрегации;
  - Memory: `factIds = [memory:<id>]`, и дополнительно `capture:<sourceCaptureId>`, **только если**
    `Memory.sourceCaptureId` реально записан (существующая связь Этапа 6) — никогда не выдумывается.
- `ReviewFinding` (`packages/domain/src/review.ts`) получил `evidenceFactIds: readonly string[]` —
  объединение `factIds` по всем процитированным `evidenceRefs`, вычисленное один раз в `finishReview`
  (`application.ts`) из того же пересобранного evidence pack, что уже валидирует `evidenceRefs`; никогда
  не доверяется ИИ. Персистентность — колонка `review_findings.evidence_fact_ids`
  (миграция `0014_review_finding_fact_ids`, `DEFAULT '[]'` для строк до фикса — они просто перестают
  засчитываться в независимость, пока разбор не пройдёт снова, без выдуманной provenance).
- `maybeSurfacePatternCandidate` теперь группирует и сравнивает `evidenceFactIds` (а не `evidenceRefs`)
  по Review — тот же алгоритм независимости, что H1-фикс уже использовал для ссылок, применённый к
  канонической идентичности факта. Правило по-прежнему fail-closed: пропустить кандидата безопаснее,
  чем создать ложный личный закон из одного факта.

Покрыто регрессионными тестами на реальном SQLite (`packages/persistence-sqlite/test/review.test.ts`,
описание "H2: canonical underlying-fact identity"): один рабочий интервал, процитированный дневным
разбором напрямую и агрегированный в недельный `worktotal`, не даёт повторения (но два по-настоящему
разных интервала — дают); Capture и явно выведенная из неё Memory не дают повторения (но по-настоящему
не связанная вторая Capture — даёт); повторная попытка после `failed` не создаёт вторую находку и не
раздувает повторение.

### M2 — правка формулировки сезона ≠ смена сезона

`season.updateFocus` (правка текста) больше не входит в `SEASON_COMMANDS` (`review-evidence.ts`) — только
`season.create` и новый `season.changeSeason` закрывают/открывают интервал для `dueSeasonalPeriods`.
`updateSeasonFocus` (`application.ts`, `UpdateSeasonFocusInputSchema`) получил `startsNewSeason: boolean`
(по умолчанию `false`) — явный выбор владельца в момент сохранения, потому что система не может надёжно
отличить «переформулировал то же самое» от «сезон реально сменился». UI (`SeasonSection`, `App.tsx`) —
чекбокс «Это смена сезона, а не просто уточнение формулировки», по умолчанию снят. Сама доменная функция
`updateSeasonFocus` не менялась — различие только в том, какой `commandType` записывается в change_log.
Сезонный разбор всё ещё может спросить «нужен ли новый сезон» — этот вопрос задаёт сам разбор текстом, а
не механика границы.

### M4 — пользователь видит факты, а не только счётчик

`ReviewFindingDto` получил `evidenceItems: {id, text}[]` — человекочитаемые факты, на которые ссылается
находка, разрешённые заново из живого evidence pack (`findingEvidenceItems`, `application.ts`) —
никогда не второй источник истины и не бизнес-логика в React. `PatternDto` получил `supportingFindings`
— по каждой независимой находке: её текст (принятый/исправленный), период разбора и её собственные
`evidenceItems`. Ссылка на исчезнувший факт (например, забытую память) молча пропускается, а не
показывается как висящий id. UI (`reviews.tsx`): у находки — компактный список фактов под текстом; у
Pattern-кандидата — свёрнутый по умолчанию `<details>` «Почему похоже, что это повторяется» с находками
и их фактами по каждому эпизоду — не превращается в audit log.

### M5 — семантика «Исправить»: правка слов vs правка сути

`correctFinding` (`packages/domain/src/review.ts`) получил `keepPattern: boolean` — явный выбор владельца
в момент правки, не вывод ИИ и не heuristика. `keepPattern: true` сохраняет `patternKey` (правка только
формулировки, факт тот же); по умолчанию (`false`) `patternKey` сбрасывается, как раньше — консервативное
поведение, если владелец не подтвердил обратное. `CorrectReviewFindingInputSchema` — новое поле того же
имени. UI: чекбокс «Это только уточнение формулировки, суть та же», виден только когда у находки есть
`patternKey`, по умолчанию снят.

### Ответ на инвариант Gate B (до четвёртого прохода ниже — см. итоговый ответ там)

## Четвёртый проход (независимая проверка третьего прохода, до Gate B)

Отдельный fresh-context проход `code-reviewer`, специально нацеленный на попытку сломать именно этот
инвариант — не доверяя тексту третьего прохода выше. Нашёл и подтвердил кодом **3 HIGH и 2 MEDIUM**;
все HIGH и оба MEDIUM исправлены до Gate B. Итоговый тест-сьют — 359 unit/integration (было 356) +
11/11 E2E (без изменений в числе, но фикстура `reviews.spec.ts` обновлена — см. ниже).

**Исправлено:**

- **H (было HIGH) — `resolveIfProposed` (`persistence-sqlite/src/store.ts`) не писал `patternKey` в
  колонку БД при `correctFinding`, поэтому M5 (третий проход) был no-op на реальном SQLite: домен
  корректно сбрасывал `patternKey` в памяти и в возвращаемом DTO команды, но при следующей перечитке
  строки из БД (`listAcceptedByPatternKey`, `listDistinctPatternThemes`, повторное `getReview`)
  сохранялась СТАРАЯ тема ИИ.** Опровергнутая находка продолжала засчитываться как evidence темы, а её
  текст — как пример темы для будущих запусков ИИ. Исправлено добавлением `patternKey: f.patternKey` в
  `.set(...)`. Регрессионный тест (реальная БД): «M5 persists: «Исправить» with keepPattern:false clears
  patternKey in the database, not just the command's own returned DTO» (`persistence-sqlite/test/review.test.ts`).
- **H (было HIGH) — правило независимости «у каждого Review есть хотя бы один факт, которого нет у
  других» было недостаточным: агрегат (`worktotal:`) законно сворачивает НЕСКОЛЬКО интервалов действия
  за период, поэтому дневной и недельный разбор могут делить настоящий общий факт эпизода, и при этом у
  каждого будет ещё какой-то СВОЙ, посторонний факт (Capture дня / другой интервал недели), который
  делает его формально «уникальным».** Инвариант заменён на: среди Review, давших evidence по теме,
  должна найтись хотя бы одна ПАРА с ПОЛНОСТЬЮ непересекающимся `evidenceFactIds` (`hasDisjointPair`,
  `application.ts`) — не «не идентичны», а «ноль общих фактов». То же правило применено к воскрешению
  отклонённой темы (пара должна включать хотя бы один Review за пределами уже отклонённого набора). Как
  побочный эффект чинит недетерминированность по порядку подтверждения (два дня с фактами `{a}`/`{b}` и
  недельный `{a,b}` теперь дают кандидата независимо от порядка accept). Регрессионный тест: «pairwise-
  disjoint independence: a daily and a weekly review that both cite the true shared episode fact are NOT
  independent merely because each ALSO cites something unrelated».
- **H (было HIGH) — Proposal, созданный из Capture (`Capture.proposalId`, Этап 6), не нёс это в
  `factIds`: Proposal и Capture, из которой он произошёл, представляли один и тот же эпизод под двумя
  несвязанными id.** `CaptureReader.findByProposalId` (новый метод порта) даёт `buildReviewEvidence`
  найти исходную Capture проекта и добавить `capture:<id>` в `factIds` proposal-евиденс-item'а — тот же
  приём, что уже был у Memory→Capture. Отдельно: `proposal.create` добавлен в
  `REDUNDANT_OR_TECHNICAL_COMMANDS` — эта changelog-запись дублировала уже показанный `proposal:<id>`
  под третьим, несвязанным id (`changelog:<entry.id>`) с тем же эффектом. Регрессионный тест: «Capture →
  Proposal provenance: a Capture and the route Proposal explicitly created from it are NOT independent
  evidence; an unrelated Proposal still is».
- **M (было MEDIUM) — evidence, показанная владельцу (`findingEvidenceItems`), молча теряла ссылки на
  исчезнувшие записи (например забытую Memory), из-за чего пользователь видел МЕНЬШЕ фактов, чем
  реально учёл движок Pattern при принятии решения о независимости.** Теперь на каждый `evidenceRef`
  находки всегда приходится ровно один элемент `evidenceItems` — при исчезнувшей записи вместо тихого
  пропуска показывается «Факт больше недоступен (например, забытая память).», а не молчаливое
  уменьшение списка.
- **L (было LOW) — `season.changeSeason` в истории изменений показывался как generic «Изменение».**
  Добавлена метка «Начат новый сезон» (`App.tsx`, `HISTORY_LABELS`).

**Задокументировано, не исправлено (осознанно принятый остаточный риск):**

- **M (`Memory.sourceCaptureId` надёжен только внутри запуска разбора конкретной Capture)** — вне этого
  (интерактивная MCP-сессия, где ИИ сам выбирает `captureId` как обычный ввод) связь опирается на то,
  что ИИ передал корректный `captureId`. **Направление ошибки здесь исправлено пятым проходом ниже: не
  переданный `captureId` НЕ безопасен** — он даёт ложноположительный результат (Capture и её Memory без
  связи выглядят как два независимых факта, ровно то, что инвариант запрещает), а не ложноотрицательный,
  как ошибочно утверждала эта запись. Привязка к чужой Capture по-прежнему только подавляет кандидата,
  никогда не создаёт его — эта часть верна. Не исправляется без отдельного решения владельца об
  ограничении `saveMemory` вне запуска Capture — остаётся открытым, зафиксированный, риском.
- Порядок обхода `evidenceFindingIds` внутри Pattern (все совпадающие находки, включая не входящие в
  «независимую пару») остаётся как раньше — `supportingFindings` (M4) показывает их все, а не только
  формально независимую пару; это осознанно шире, чем строгий минимум, который доказывает независимость,
  чтобы не прятать от владельца реально принятое во внимание доказательство.

## Пятый проход (независимая пост-фикс проверка перед Gate B, закрывает пробел верификации)

Четвёртый проход выше сам и написал фиксы, и написал вердикт «инвариант доказан» — один и тот же контекст

кода (после всех фиксов выше), реальными вызовами команд на реальном SQLite, а не чтением текста ADR.

**Нашёл и подтвердил кодом (запустив репро-скрипты против реального SQLite) 3 HIGH и 3 MEDIUM.** Все три
HIGH и два из трёх MEDIUM (M-B, M-C) исправлены; один MEDIUM (M-A) — уже известный, сознательно
отложенный риск, но с исправленным в этом же проходе направлением ошибки (см. правку выше). Итоговый

**Исправлено:**

- **H-A — Capture и `plan.reorder`, выполненный ИИ-задачей ЭТОЙ ЖЕ Capture, не были связаны.**
  `reorder_existing_actions` — единственный, наряду с `memory.save`/`proposal.create`, SAFE WRITE,
  доступный `mcp-ai` (`policy.ts`), но его `change_log`-запись не несла обратной связи с Capture, в
  отличие от Memory/Proposal (H2). Реальный репро: Capture с текстом «Сначала A2 — перестрой порядок» →
  `reorder_existing_actions` тем же ИИ-запуском → дневной разбор цитирует `capture:<id>`, недельный
  цитирует `changelog:<id>` той же самой перестановки под тем же `patternKey` → ложный кандидат из одного
  события. Добавлена колонка `change_log.source_capture_id` (миграция `0015_change_log_source_capture_id`,
  `NULL` для всех существующих строк и для записей не из Capture — никогда не выдумывается), заполняется
  из `ctx.captureId` в единственном месте записи `plan.reorder`
  (`application.ts`), и `buildReviewEvidence` (`review-evidence.ts`) добавляет `capture:<id>` в `factIds`
  changelog-элемента, когда связь есть — тот же приём, что и Memory/Proposal.
- **H-B — пустой `evidenceFactIds` (например, строка, записанная до миграции 0014, `DEFAULT '[]'`)
  засчитывался как «непересекающийся» с ЛЮБЫМ другим фактом.** `disjoint()` (`application.ts`) сравнивал
  множества через цикл по первому — пустое множество тривиально «не пересекается» ни с чем, то есть было
  МАКСИМАЛЬНО «независимым», хотя означает ровно противоположное: неизвестную провенансность. Это
  регрессия, которую сам переход на попарную непересекаемость (четвёртый проход) незаметно ввёл — при
  старом правиле «≥2 разных ref в объединении» пустой набор такого преимущества не давал. Исправлено:
  `disjoint(a, b)` теперь `false`, если любое из множеств пусто — неизвестная провенансность никогда не
  доказывает независимость (тот же fail-closed принцип, что и везде в этом этапе).
- **H-C — восстановление отклонённой темы проверялось по id Review, а не по id факта — та же ошибка,
  которую H2 исправил для основной проверки, но пропущенная здесь.** `rejectedReviewIds` требовал только
  «хотя бы один Review пары не входит в отклонённый набор Review'ов» — но Review, не входящий в набор,
  мог всё равно цитировать ФАКТ, который уже был учтён в отклонении (под другим reviewId). Реальный
  репро: неделя 1 цитирует факт A, неделя 2 (другой Review) цитирует факт Б → кандидат → отклонён; третий
  Review повторно цитирует ТОЛЬКО факт Б (тот же, уже отклонённый) → воскрешение с нулём новых фактов.
  Исправлено: `rejectedFacts` теперь множество ФАКТОВ (объединение `evidenceFactIds` находок отклонённого
  паттерна), и воскрешение требует непересекающуюся пару, где хотя бы одна сторона содержит факт,
  которого нет в `rejectedFacts` (`hasNewFact`, `application.ts`). Побочный эффект, обнаруженный
  существующим тестом `application/test/review.test.ts` («…resurfaces only once a genuinely new
  Review…»): этот тест сам оказался написан на прежней, слишком грубой семантике «Review, а не факт» —
  переименован и его ожидание исправлено (сиблинг-находка из уже учтённого Review, но с ДЕЙСТВИТЕЛЬНО
  новым фактом, теперь корректно засчитывается как независимое доказательство, а не блокируется навсегда).
- **M-B — завершение Действия (`action:<id>`) и его же рабочий интервал (`worksession:`/`worktotal:`) не
  были связаны.** Нажатие «Готово» во время работающего таймера — одно и то же прожитое событие с точки
  зрения дневного разбора (цитирует `action:`) и недельного (агрегирует тот же интервал в `worktotal:`).
  `buildReviewEvidence` теперь строит карту интервалов по Действию заранее и добавляет их `interval:<id>`
  в `factIds` элемента `action:<id>` — тот же приём, симметричный уже существующей стороне
  `worktotal`/`worksession`.
- **M-C — счётчик «Основано на N находках из разных разборов» (`reviews.tsx`) был буквально ложным: N —
  это ВСЕ подходящие находки, включая несколько из одного и того же Review** (тогда как «из разных
  разборов» подразумевает N разборов). Исправлено на подсчёт различных `reviewId` среди
  `supportingFindings` отдельно от общего числа находок — чисто отображение, `PatternDto`/движок не
  менялись.

**Задокументировано, не исправлено (см. правку M-A выше):** направление риска `Memory.sourceCaptureId`
вне запуска Capture было названо неверно (ложноотрицательный → на деле ложноположительный) — сам риск
остаётся открытым, решение владельца об ограничении `saveMemory` не в рамках этого прохода.

## Шестой проход (закрытие M-A перед Gate B): association ≠ verified provenance

Пятый проход (выше) оставил M-A как сознательно принятый открытый риск. Владелец не согласился считать
его закрытым молча в четвёртый раз и потребовал: сначала доказать эксплуатируемость кодом (не
рассуждением), затем, если реальна, закрыть архитектурным решением, а не патчем поверх текущей модели
доверия.

**Доказательство эксплуатируемости.** Реальный репро против временной SQLite (`packages/application`
commands, без обращения к живой БД): Capture C → интерактивный `mcp-ai`-контекст без `ctx.captureId`
(в точности то, что отдаёт `apps/mcp/src/main.ts`, когда `LIVING_MAP_CAPTURE_ID` не установлена — ровно
то, как подключён MCP-сервер репозитория через корневой `.mcp.json`, задокументированный способ
разработческого/интерактивного доступа, ADR-0004) сохраняет Memory M с тем же фактом, `captureId: null`
→ два разбора цитируют C и M раздельно под одним `patternKey` → создаётся Pattern-кандидат из одного
события. Ключевое новое наблюдение: это не гипотетический будущий путь — `.mcp.json` уже открывает
именно эту MCP-поверхность против РЕАЛЬНОЙ `%APPDATA%\LivingMap\living-map.sqlite` (та же БД, что и у
desktop, ARCHITECTURE §9), и это тот же способ, которым, по ADR-0004, подключается личный чат владельца
(Claude Desktop) к его собственным данным.

**Архитектурное решение владельца.** Не ограничивать и не убирать интерактивную Stage-6-способность
(«ИИ из чата может привязать Memory к старой `+`-записи по id», ADR-0004) — вместо этого разделить два
разных понятия, которые `Memory.sourceCaptureId` раньше смешивал в одном поле:

1. **Связь/ассоциация** («эта Memory связана с этой Capture») — продуктовая Stage-6-функция, видимая
   пользователю под Capture; устанавливается АААйным `captureId` из любой сессии, как и раньше.
2. **Проверенная провенансность** («эта Memory доказанно про то же самое прожитое событие») —
   используется ТОЛЬКО движком независимости Pattern (`review-evidence.ts`). Устанавливается только
   когда связь пришла из доверенного контекста запуска (`ctx.captureId`, тот же самый механизм, что уже
   даёт H2/H-A), — никогда из голого утверждения ИИ через `SaveMemoryInput.captureId` в сессии без этого
   контекста, даже если утверждение окажется правдой. Как явно принято владельцем: путь Б («владелец
   явно подтверждает: эта Memory действительно из этой Capture») в модели предусмотрен, но в этом
   проходе не реализован — интерактивная связь просто никогда не становится provenance сама по себе,
   пока это отдельно не запрошено.

**Реализация (минимальная, без общего provenance-фреймворка):**

- `Memory.sourceCaptureVerified: boolean` (`packages/domain/src/memory.ts`) — не может быть `true` без
  `sourceCaptureId` (нормализуется в `createMemory`).
- `saveMemory` (`application.ts`) вычисляет `sourceCaptureVerified = ctx.captureId !== undefined` —
  ТОЛЬКО собственный доверенный контекст запуска, никогда `input.captureId`.
- Миграция `0016_memory_source_capture_verified` (`memories.source_capture_verified`, `NOT NULL DEFAULT
  false`) — с бэкфиллом `= 1` там, где `source_capture_id` уже задан: внутри самого приложения
  единственный путь когда-либо задать эту колонку — доверенный запуск (интерактивный путь не был
  реально подключён к реальной БД до этого прохода), так что дефолт `false` для существующих строк
  тихо уронил бы уже доказанную H2/H-A provenance в момент этой самой миграции.
- `review-evidence.ts`: `factIds` Memory включает `capture:<id>` только при `sourceCaptureVerified`;
  иначе Memory остаётся сама по себе, как если бы связи не было вовсе — честнее прежнего поведения,
  которое слепо доверяло любому непустому `sourceCaptureId`.
- Дедупликация «одна Memory на тип на Capture» (`saveMemory`) при попадании в уже существующую
  неподтверждённую запись, если ЭТОТ запуск доверенный, повышает её до `verified`
  (`s.memories.verifySourceCapture`) — иначе собственное доверенное подтверждение более позднего запуска
  тихо терялось бы. Пишет `change_log` под отдельным `commandType` `memory.verify` (не `memory.save`,
  чтобы не задваивать «ИИ сохранила в память» в истории пользователя) — исключён из Review evidence
  (`REDUNDANT_OR_TECHNICAL_COMMANDS`) и из истории/MCP-контекста (`UNLISTED_COMMANDS`), обязателен по
  структурной гарантии ARCHITECTURE §44 (любая запись строки обязана сопровождаться `recordChange`).

**Независимая свежая проверка (дважды).** Первый проход нашёл фикс концептуально верным, но
сформулировал само решение владельца («интерактивная связь не provenance») как «регрессию» — это не
баг, а осознанно принятый компромисс: он честно перестаёт слепо доверять любому утверждению ИИ (верному
или нет) вместо избирательного доверия только удачным случаям. Тот же проход нашёл два реальных, не
предусмотренных изначально дефекта, оба исправлены до записи этого раздела:

- Дефолт миграции `false` тихо уронил бы provenance уже существующих (реально доверенных) Memory —
  исправлено бэкфиллом выше.
- Апгрейд при дедупликации не проводился, если совпадение уже существовало — то есть собственное
  доверенное подтверждение более позднего запуска тихо терялось; исправлено (`verifySourceCapture` +
  `recordChange`).

Второй проход, специально нацеленный на эти два патча, подтвердил оба верными и нашёл три LOW: неточная
формулировка комментария миграции (утверждала, что интерактивный путь «никогда не был подключён к
реальной БД» — на деле подключаем через `.mcp.json`, просто не как часть поведения самого продукта;
формулировка исправлена), апгрейд писал `commandType: "memory.save"` вместо отдельного типа (дублируя
«ИИ сохранила в память» в истории — исправлено на `memory.verify` + `UNLISTED_COMMANDS`), и отсутствие
теста на то, что `stateRevision` не двигается при повторном доверенном запуске после апгрейда (добавлен).

**Что сознательно НЕ закрыто (не входит в этот проход, не техническая недоработка):** если ИИ в любой
сессии вообще не передаёт `captureId` (не связывает Memory ни с чем, хотя по содержанию она про
конкретную Capture), система не может это обнаружить без семантической эвристики — запрещённой §2/§48
и этим ADR явно. Это структурный предел «provenance только из явной известной связи», а не пропуск
кода: если связь не заявлена явно нигде, её негде взять. Путь Б (явное подтверждение владельцем) мог бы
закрыть и этот случай, но не реализован в этом проходе — отдельная продуктовая функция, не инвариант.

Формулировки на экране «Разборы» ощущаются как бюрократический официальный инструмент, хотя технической
терминологии там уже нет. Желаемое направление — разговорный, дружелюбный тон («умный друг объясняет, что
произошло», а не «официальная система описывает рабочий процесс»): короче, естественный русский, меньше
отглагольных существительных и формальных ярлыков, меньше канцелярита/отчётности, прямые обычные глаголы.
Примеры направления (не готовые финальные формулировки): «Подтвердить вывод» → «Да, это правда»;
«Игнорировать» → «Нет, не про меня»; «Кандидат в закономерность» → «Похоже, это повторяется»; «Сделать
правилом» → «Учитывать это дальше». Правки текста в рамках этого прохода Gate B не делались — находка
зафиксирована для отдельной работы до Gate C.

## Чекпойнт Gate B: реальная миграция применена, ожидание естественного повторения

После прохода выше миграция Этапа 7 реально применена к рабочей БД (не только read-only-проверена):
подтверждено только что повторным read-only чтением той же `%APPDATA%\LivingMap\living-map.sqlite` —
`PRAGMA user_version = 17` (было 13 до Этапа 7), таблицы `reviews`/`review_findings`/`patterns`/
`planning_rules` существуют и населены: `reviews` — 3 строки, `review_findings` — 5 (`accepted`: 1,
`rejected`: 4, совпадает с разделом выше), `patterns` — 0, `planning_rules` — 0.

На реальных прогонах нашлись и были исправлены два отдельных транспортных бага задачи ИИ Review — ниже
оба зафиксированы явно, так как предыдущие проходы этого ADR описали только второй.

**Баг 1 (схема, первым блокировал любой реальный прогон).** `ReviewAiResultSchema`
(`packages/contracts/src/review.ts`) — это `z.discriminatedUnion`, чей сгенерированный JSON Schema для
custom-tool API структурированного вывода — корневой `oneOf` без верхнеуровневого `type: "object"`,
которого требует транспорт (реальная ошибка: `tools.0.custom.input_schema.type: Field required`).
Исправлено добавлением `ReviewAiTransportSchema = z.strictObject({ result: ReviewAiResultSchema })`
(`packages/contracts/src/review.ts`) — чисто транспортной обёртки для самого API-вызова; каноническая
строгая `ReviewAiResultSchema` остаётся внутри поля `result` без изменений, семантическая валидация не
ослаблена, только дан объектный корень (`interpretReviewCliOutput`, `claude-code-cli.ts`, разбирает
`ReviewAiTransportSchema` и разворачивает `.result`).

**Баг 2 (отдельный, найден после фикса бага 1).** В дополнение к `requireMcp: false`, уже описанному в
§3/§4 выше, — тот же класс проблемы: логика транспорта, общая с Capture, неверно требовала статус
MCP-сервера, которого у Review нет и не должно быть. После обоих фиксов реальные Review успешно
обрабатываются задачей ИИ до конца (3 Review, 5 находок записаны).

**Текущее состояние Gate B (без изменений с прохода владельца выше):** 1 принятая находка
(`memory-trust-testing`) имеет пока только один независимый эпизод (один Review); кандидата Pattern нет
(`MIN_PATTERN_EVIDENCE` требует ≥2 независимых Review); PlanningRule нет. Это ожидаемое, а не блокирующее
состояние — Gate B намеренно ждёт естественного повторения, а не создаёт его искусственно (см. правило
ниже). Коммит и push для незакрытого этапа не делались.

### Правило для будущего Pattern-кандидата: подтверждённая находка ≠ автоматически достойна PlanningRule

Владельческий инвариант, который нужно применить, когда (и если) когда-нибудь появится настоящий
Pattern-кандидат из ≥2 независимых эпизодов: то, что находка правдива и подтверждена владельцем, само по
себе НЕ достаточное основание превращать её в `PlanningRule`. `PlanningRule` должен представлять
обучение, способное реально изменить будущее решение (пример: реалистичная рабочая ёмкость, повторяющееся
ограничение, последовательность действий, которая надёжно работает/не работает, условия, при которых
действие становится нереалистичным, повторяющийся блокер, подтверждённое предпочтение). Истинное
наблюдение, которое лишь описательно/интересно/про доверие к интерфейсу и не способно изменить будущее
решение, НЕ должно становиться `PlanningRule` только потому, что оно повторилось.

Когда реальный Pattern-кандидат появится, перед тем как звать владельца подтвердить: (1) проверить, что
он идёт минимум от двух по-настоящему независимых пережитых эпизодов, провенанс не пересекается, owner
видит конкретные факты за обоими, а перезапуск/переобработка не сфабриковали повторение (правила уже
реализованы, §H1–H2/H-A–H-C выше) — и (2) отдельно задать вопрос «может ли этот повторяющийся паттерн
реально улучшить будущее решение?». Если ответ «нет» — зафиксировать как product-semantic находку и
продолжать ждать, не превращать в `PlanningRule` только ради формального закрытия Gate B. Если «да» —
как обычно, решение о подтверждении остаётся за владельцем. Эта оценка — вопрос, который нужно задать
руками (в разговоре с владельцем) в момент появления кандидата; отдельная система критериев eligibility
сейчас не реализуется.

## Седьмой проход: владелец меняет стратегию закрытия Gate B — не ждать дни разработки

Владельческое решение, отменяющее предыдущий чекпойнт «GATE B WAITING FOR REAL REPEATED EVIDENCE» выше
как способ закрытия РАЗРАБОТКИ (не как описание реального состояния жизни — оно не изменилось). Ждать
дни, пока в реальной жизни владельца естественно случится второй независимый эпизод той же темы, признано
неверным способом мерить готовность механизма: он уже полностью реализован и проверен на реальной БД (см.
проход выше) везде, КРОМЕ собственно двух независимых эпизодов одной темы — которых пока просто не было.

**Явное разделение (владельческое решение):**

1. **Реальная БД (уже проверено, без изменений):** миграция 13→17 реально применена и подтверждена
   read-only чтением; реальный бэкап перед миграцией (`runMigrations`, см. проход выше); реальный
   scheduler (`scheduleDueReviews`) создал реальные периоды; реальная задача ИИ Review обработала их
   после фикса транспортного бага (`requireMcp`, см. выше); evidence реально показывается владельцу;
   владелец реально протриажил все 5 находок (1 принята — `memory-trust-testing`, 4 отклонены);
   персистентность подтверждена двумя независимыми холодными чтениями. Это не повторяется и не
   имитируется — оно уже случилось.
2. **Детерминированная проверка механизма** (этот проход): два по-настоящему независимых пережитых
   эпизода → Pattern-кандидат → подтверждение владельца → активный `PlanningRule` → видимость в будущем
   планировании → доказано, что `CurrentActionSelector` не читает `PlanningRule` и не становится вторым
   планировщиком — всё это теперь проверено на одноразовой временной SQLite-БД (`mkdtempSync`, НЕ
   реальная БД владельца), через настоящие `application`-команды/домен/persistence, без единой ручной
   записи в БД в обход этих команд. Детерминированный тестовый актёр нажимает «подтвердить»/«отклонить»
   вместо владельца — это проверка механики продукта, а не утверждение, что владелец прожил это в жизни.
3. **Естественное продольное качество (Stage 9, сознательно отложено):** способна ли РЕАЛЬНАЯ, естественно
   повторившаяся тема стать полезным `PlanningRule` в реальной жизни владельца — по-прежнему не проверено
   и не может быть проверено сегодня; остаётся заявкой на «7 дней реальной жизни + уборка» (Stage 9).
   Сегодняшний проход НЕ заявляет, что естественный Pattern уже наблюдался.

**Реализация детерминированной проверки:**
`packages/persistence-sqlite/test/review.test.ts`, describe-блок «Review persistence (real SQLite)»,
два новых теста добавлены к уже существовавшему `full pipeline` тесту (тот использовал два
`season.updateFocus` как эпизоды — тоже настоящий сквозной прогон, просто с менее «планировочно значимым»
примером темы):

- **Позитивный:** «planning-relevant lesson: two independent short-work-window episodes → Pattern
  candidate → confirm → active rule visible to future planning, without touching CurrentActionSelector».
  Тема выбрана намеренно planning-relevant (см. правило выше — не любое правдивое наблюдение достойно
  `PlanningRule`): два разных Действия, каждое с собственным коротким (12 и 10 минут) рабочим
  интервалом — канонически разные факты (`interval:<id>` разные), реально созданные через
  `startWork`/`completeAction`/`pauseWork`, реально зацитированные daily-разборами, реально принятые
  через `acceptReviewFinding`, реально давшие Pattern-кандидата с `supportingFindings` от обоих Review,
  реально подтверждённые через `confirmPattern`, реально видимые в `getPlanningContext().activePlanningRules`
  и переживающие переоткрытие файла БД. Отдельная проверка: `getCurrentView().currentAction` после
  подтверждения правила — не нарушен (это дополнительная санity-проверка; сама структурная гарантия
  «не второй планировщик» — в том, что `computeCurrentAction`/`selectCurrentAction`
  (`packages/domain/src/current-action.ts`) вообще не принимают `PlanningRule` как параметр).
- **Негативный:** «negative counterpart: the same underlying work interval cited by a daily finding and
  its weekly worktotal aggregate never forms a Pattern candidate on its own» — тот же интервал, две формы
  представления (`worksession:` vs `worktotal:`), ноль кандидатов, тот же H2-инвариант, что и выше, теперь
  ещё раз доказан на planning-relevant теме, а не только на исходном примере «приёмы у врача».

**Независимая проверка (fresh-context `code-reviewer`, отдельно от прохода, который писал тесты и правки
копирайта ниже).** Вердикт: COMMENT, ноль MEDIUM/HIGH проблем корректности кода. Подтверждено: оба новых
теста реально проходят через настоящие пути кода (не мок), независимость эпизодов реально обеспечена
несовпадающими `evidenceFactIds` (а не просто разными `evidenceRefs`), «нет второго планировщика» —
реальная структурная гарантия сигнатуры (не только проходящий assert), негативный тест — реально тот же
интервал, а не случайно неудачный кандидат по другой причине. Найдены и в этом же проходе исправлены три
LOW: комментарий теста переформулирован, чтобы не переоценивать, что именно доказывает один assert
(структурная гарантия — в сигнатуре `computeCurrentAction`, не в самом assert); склонение «2 разных
разбора» вместо «2 разных разборов» (и «раза» вместо «раз») — добавлен маленький `pluralize` хелпер;
запятая в «Может, стоит:». Один MEDIUM был процессный, не код: этот ADR не фиксировал владельческое
решение о смене стратегии Gate B — закрывается этим самым разделом.
