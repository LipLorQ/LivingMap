# ADR-0006 — Исполнятор: модель рабочего времени

**Статус:** принято (Этап 5)
**Дата:** 2026-09-28

## Решение

Рабочее время хранится как строки `work_intervals` — один непрерывный отрезок работы над одним Action:
`action_id`, `started_at`, `ended_at` (`NULL` = идёт сейчас), `last_heartbeat_at`, `time_zone`.

- **Начать / Продолжить** — вставка нового интервала; **Пауза** — закрытие текущего. «Сессия» по действию —
  это просто все его интервалы. Отдельной сущности WorkSession и отдельного статуса «на паузе» нет:
  idle / running / paused выводятся из интервалов.
- **Не больше одного идущего интервала глобально** — факт БД: частичный уникальный индекс
  `ON work_intervals((1)) WHERE ended_at IS NULL`. Приложение дополнительно проверяет это и отвечает
  `CONFLICT_RELOAD` на двойной клик / устаревший UI.
- **Начать** разрешено только для действия, которое сейчас показано как `Сейчас` (тот же
  `computeCurrentAction` поверх `CurrentActionSelector`). Идущая работа «прикалывает» `Сейчас`: пока интервал
  открыт, смена порядка ИИ не уводит карточку на другое действие (`reason: working`). Второго алгоритма выбора нет.
- **Готово** — существующая команда `completeAction`; если по действию идёт работа, интервал закрывается в той же
  транзакции (одна команда = одна ревизия). **Заблокировать** идущее действие тоже закрывает интервал.
  Завершить действие без единого интервала можно.
- **Сумма по действию** = все его интервалы. **Сегодня / неделя** — пересечение интервалов с локальными сутками
  (неделя с понедельника). Каждый интервал считается в своём сохранённом `time_zone`, поэтому история не
  «переезжает» на другую дату при смене часового пояса. Время хранится в UTC.
- **Норма** — одна строка `settings.daily_work_target_minutes` (старт 360), меняется пользователем; на записанное
  время не влияет. MCP её менять не может.

## Жизненный цикл (решения владельца, Gate A)

- Потеря фокуса / свёрнутое окно — таймер идёт.
- Выход из приложения (`will-quit`) и сон ОС (`powerMonitor` `suspend`) — синхронная пауза; после пробуждения
  автопродолжения нет.
- Сбой / потеря питания — при следующем запуске открытый интервал закрывается по `last_heartbeat_at`
  (`work.recover`), состояние — пауза. Checkpoint обновляется раз в минуту.
- Если checkpoint старше 3 минут (`WORK_HEARTBEAT_GAP_MS`, домен) — пропущенное событие сна, заморозка, убитый
  процесс, скачок часов вперёд — время после checkpoint не считается нигде: ни в чтениях (`execution`, в т.ч. в
  контексте ИИ, где такой интервал показан как пауза), ни при «Пауза» / «Готово» (закрытие по checkpoint), ни при
  «Продолжить» (молчащий интервал сначала закрывается по checkpoint как `work.recover`). Очередной тик, а также
  `powerMonitor` `resume` / `unlock-screen` сразу закрывают такой интервал; автопродолжения нет.
- Скачок часов назад: интервал никогда не становится отрицательным; время может недосчитаться, но не выдумывается.

## Heartbeat — техническая метаинформация

`Store.touchWorkHeartbeat` — отдельная от `write()` однострочная запись: не увеличивает `state_revision`, не пишет
`change_log`, не видна в истории и в контексте ИИ. В историю попадают только смысловые события:
`work.start`, `work.resume`, `work.pause`, `work.recover`, `action.complete`, `settings.dailyWorkTarget`.

## MCP

Только чтение: `execution` входит в `get_living_map_context` (состояние, сумма по действию, сегодня, неделя,
норма). Команд управления исполнением у `mcp-ai` нет (`policy.ts`).

## Известные ограничения

- Ручного редактирования прошлого времени нет (решение владельца).
- Второй запуск desktop-приложения не открывает БД: `app.requestSingleInstanceLock()` передаёт фокус уже открытому
  окну. Lock привязан к `userData`; при переопределённом `LIVING_MAP_HOME` (тесты) `userData` лежит внутри него.
- «Начать» / «Пауза» / «Продолжить» — смысловые события и увеличивают `state_revision`, поэтому write-инструмент
  ИИ, прочитавший контекст до нажатия, получит `CONFLICT_RELOAD` и перечитает. Предложения при этом не устаревают
  (отпечаток контекста не включает исполнение).
