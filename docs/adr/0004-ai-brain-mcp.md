# ADR-0004 — ИИ-мозг через MCP: OrderedActionPlan, Proposal, полномочия MCP

**Статус:** принято (Этап 3, 28.09.2026)
**Уточняет:** ARCHITECTURE.md §22–25, §25.1, §31, §39, §50.3; ADR-007/008/011/015; ADR-0003 (MCP-поверхность и dev-install)

## Контекст

Этап 3 делает внешний MCP-совместимый ИИ мозгом маршрута: ИИ читает Живую карту, предлагает маршрут и порядок, пользователь подтверждает. ИИ не должен молча менять стратегию.

## Решения

### 1. OrderedActionPlan — единственный стратегический порядок

- Таблица `ordered_action_plans`, **одна строка на Замысел** (unique `intention_id`, FK cascade): `id, intentionId, orderedActionIds (JSON), rationale, createdBy, createdAt, updatedAt, version, sourceRevision`.
- Инвариант записи (domain `validateActionOrder`): `orderedActionIds` — ровно перестановка **незавершённых** (open/blocked) действий Замысла на момент записи: без дублей, без чужих, без завершённых, без пропусков. Завершённые действия в новый порядок не входят; план, который со временем содержит завершённые id, остаётся читаемым (будущий CurrentActionSelector их пропускает).
- `createdBy` — автор текущего порядка (каждая версия — целиком новый порядок); `sourceRevision` — ревизия мира, на которой порядок продуман.
- Незавершённые действия, которых нет в плане (например, пользователь добавил вручную), выдаются как производное `unplannedActionIds`: ИИ видит их в контексте, UI просит обновить порядок. Отдельного хранимого флага «нужно перепланирование» нет.
- Per-action rationale («почему сейчас») сознательно не хранится — это Этап 4 (§28), см. `FUTURE_IDEAS.md`.

### 2. Отношение к `position` (ADR-015)

- `Action.position` — **только порядок показа внутри этапа** (UI-хранение/отладка). Он не влияет на стратегию и не мигрирует в план.
- `Stage.position` — последовательность этапов маршрута (структура, которую пользователь может менять вручную, а ИИ — только через Proposal).
- Существующий ручной порядок Этапа 2 **не переинтерпретируется** как решение ИИ: после миграции плана нет (`orderedActionPlan = null`) до первого подтверждённого маршрута.

### 3. Proposal

- Таблица `proposals`: `id, kind, status, createdBy, createdAt, baseRevision, baseFingerprint, affectedEntityIds (JSON), payload (JSON), rationale, resolvedAt, resolvedBy`.
- Виды (минимум для этапа): `route` (первый маршрут и перепланирование) и `desired_result`. Payload — строго типизированные Zod-схемы (`RoutePayloadSchema`, `DesiredResultPayloadSchema`), проверяются при создании и **повторно** перед применением; повреждённый payload никогда не применяется (предложение становится stale).
- Статусы: `pending → accepted | rejected | stale`, прочие переходы запрещены (domain `resolveProposal`); запись статуса — `UPDATE … WHERE status='pending'`.
- Новые сущности получают UUID уже при создании предложения; ИИ ссылается на них короткими `ref` (≤32 символа, поэтому не спутать с UUID).
- Лимит: не более 10 ожидающих предложений. Перед созданием нового предложения все ожидающие, которые уже не могут примениться (устаревшие или нечитаемые), сохраняются как `stale` — они не занимают лимит и не висят невидимо.
- «Отклонить» на предложении, которое уже не может примениться, записывает его как `stale`, а не `rejected` (история честно говорит «устарело»). Повторное принятие/отклонение уже решённого (двойной клик) → `CONFLICT_RELOAD`; кнопки в UI блокируются на время запроса.
- Правка в маршруте, которая ничего не меняет (то же название / тот же «готово, когда»), отклоняется доменом.

### 4. Устаревание (stale) без молчаливого rebase

- `baseFingerprint` = отсортированные пары `id@version` всего планировочного контекста Замысла: Season, Good Life Conditions, Intention, его Stages, Actions и plan. Любое изменение/добавление/завершение/перестановка → отпечаток другой → предложение устарело. Сознательно консервативно.
- Другие предложения в отпечаток не входят: создание предложения не делает устаревшими остальные; принятие одного — делает.
- Чтение сообщает эффективный статус `stale` сразу (UI и ИИ не видят его как применимое); при попытке принять статус сохраняется как `stale`, возвращается `STALE_PROPOSAL`.
- `baseRevision` хранится для информации и как `sourceRevision` плана; материальность изменения определяется отпечатком, а не сравнением ревизий (ревизию двигают и нестратегические записи, например создание других предложений).
- При создании предложения ИИ передаёт `expectedRevision` из прочитанного контекста; несовпадение → `CONFLICT_RELOAD` (ИИ не может предложить что-то, продуманное на устаревшем чтении).

### 5. Принятие — одна атомарная команда

`acceptProposal` (только `user-ui`): загрузить → статус pending → повторно разобрать payload → сравнить отпечаток → применить через ту же доменную функцию `applyRouteChange`, которая строила предпросмотр → создать/обновить план (с проверкой версии) → `accepted` → change log. Всё в одной IMMEDIATE-транзакции; любая ошибка откатывает всё (проверено тестом с триггером, падающим посреди применения).

**Одна команда = один bump ревизии.** `recordChange` теперь увеличивает `state_revision` только при первом вызове в транзакции; последующие записи change log в той же транзакции делят эту ревизию (порядок внутри ревизии — по `rowid`). Принятие маршрута пишет запись на каждую созданную/изменённую сущность (`proposal.accept`, entityType stage/action/plan/intention) и итоговую запись по самому предложению.

Предпросмотр («Что изменится») вычисляется при чтении той же функцией `applyRouteChange` на текущем состоянии — пользователь видит ровно то, что будет записано.

### 6. Полномочия (ARCHITECTURE §22)

| Класс | Что | Где закреплено |
|---|---|---|
| READ | `get_state_revision`, `get_living_map_context`, `get_history`, `get_proposal` | MCP whitelist |
| SAFE WRITE | `reorder_existing_actions` (policy `plan.reorder`) — только при существующем подтверждённом плане, только перестановка незавершённых действий Замысла, трогает только строку плана; требует `expectedRevision` (мир, который ИИ прочитал; он же становится `sourceRevision`) и `expectedPlanVersion`; no-op (тот же порядок и rationale) отклоняется, чтобы не делать устаревшими ожидающие предложения | whitelist + policy + domain |
| PROPOSAL REQUIRED | `create_route_proposal`, `propose_desired_result_change` (policy `proposal.create`) | whitelist + policy |
| Требует подтверждения, но у ИИ пути нет вовсе | изменение сезона, «Чем ты не хочешь жертвовать ради целей?», активация/отпускание Замысла | нет MCP-инструмента и нет policy для `mcp-ai` |
| FORBIDDEN | SQL, миграции, policy, файлы, shell, удаление, принятие/отклонение предложений, прямые доменные записи, календарь, секреты | нет инструментов; `mcp-ai` отсутствует во всех прочих командах policy |

- `mcp-ai` в policy разрешено ровно `proposal.create` и `plan.reorder` (тест). `proposal.accept/reject` — только `user-ui`/`system`.
- MCP-процесс получает не `Application`, а `AiSurface` (`packages/application/src/ai-surface.ts`): 7 функций с актором, жёстко привязанным к `mcp-ai`. Код MCP физически не может создать контекст `user-ui` или вызвать другие команды.
- Архитектурный тест запрещает в `apps/mcp/src` упоминания `acceptProposal`, `rejectProposal`, `newContext`, `.commands`, `.queries`, актора `user-ui`/`system`, SQL-драйвера, миграций/бэкапов, `.sqlite`.
- Каждая MCP-запись идёт как actor `mcp-ai` с новым `correlationId`. В истории различимы: ручные изменения пользователя (`user-ui`, обычные команды), предложения ИИ (`mcp-ai`, `proposal.create`), безопасная перестановка ИИ (`mcp-ai`, `plan.reorder`), принятое от ИИ (`user-ui`, `proposal.accept`), отклонённое/устаревшее.
- В логи/историю не пишутся разговоры с ИИ; rationale хранится только внутри предложения/плана (это продуктовые данные, показываемые пользователю).

### 7. Обновление desktop

Создание предложения — запись с `recordChange` → `state_revision` растёт → существующий 500-мс watcher шлёт `stateChanged` → renderer перечитывает `getCurrentView`, который теперь содержит план, `unplannedActionIds` и ожидающие предложения. Никакой новой шины событий.

### 8. Подключение реального MCP-host (ARCHITECTURE §50.3)

Проверено на установленном Claude Code 2.1.144 (`claude mcp --help`, `claude --help`). Проектный конфиг — `.mcp.json` в корне репозитория (scope `project`), без абсолютных путей:

```json
{ "mcpServers": { "living-map": { "type": "stdio", "command": "node", "args": ["--import", "tsx", "apps/mcp/src/main.ts"] } } }
```

- Запускает MCP из исходников через `tsx` (нет устаревшего `dist`, нет шага сборки). Claude Code стартует stdio-серверы проекта из корня репозитория; `claude mcp list` → `living-map … ✓ Connected`.
- **Работает с реальной БД пользователя** (`%APPDATA%\LivingMap`), если `LIVING_MAP_HOME` не задан — это сознательно: так пользователь обсуждает свою настоящую Живую карту в Claude Code, открытом в этом репозитории. Claude Code спрашивает разрешение на запуск project-scoped MCP-сервера из `.mcp.json`; при этом любая сессия Claude Code в этом репозитории, где сервер разрешён, может создавать предложения и безопасно переставлять утверждённый план. Для разработки/тестов задавайте `LIVING_MAP_HOME` на временную папку (автотесты делают это всегда). Desktop должен хотя бы раз запуститься после обновления (он мигрирует; MCP до этого отвечает `SCHEMA_INCOMPATIBLE`).
- Claude Desktop (чат-приложение) требует абсолютных путей в `%APPDATA%\Claude\claude_desktop_config.json` (`"command": "node", "args": ["C:\\…\\LivingMap\\apps\\mcp\\dist\\main.js"]` после `pnpm --filter @living-map/mcp build`) — это машинно-зависимая настройка, в репозиторий не коммитится.

## Независимое ревью (Этап 3)

Отдельный проход `code-reviewer`: 0 HIGH, 2 MEDIUM, 5 LOW. Исправлено: M1 (безопасная перестановка без проверки прочитанного мира и с неверным `sourceRevision`), M2 (устаревшие/нечитаемые предложения занимали лимит; нечитаемое нельзя было отклонить), L1 (no-op правки и перестановки), L2 (двойной клик), L3 (неиспользуемые поля `previous*` в хранимом payload удалены), L4 (задокументированы семантики `stateRevision()`/guard в `WriteScope`), L5 (фасад `AiSurface` + явная оговорка про реальную БД в `.mcp.json`).

## Отложено сознательно

См. `FUTURE_IDEAS.md`: per-action «почему сейчас», предложения изменения сезона/условий, блокировки и удаление в маршрутных предложениях, ручное редактирование плана пользователем в UI.

## Риски

- Консервативный отпечаток: любое правка пользователя во время обсуждения делает предложение устаревшим — ИИ придётся пересобрать. Осознанный выбор в пользу безопасности.
- `get_living_map_context` отдаёт полные тексты (результат, условия, названия) внешнему ИИ — это и есть назначение этапа; ИИ-host пользователя выбран самим пользователем.
