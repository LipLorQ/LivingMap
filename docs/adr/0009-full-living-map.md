# ADR-0009 — Полная Живая карта: одна причинная линия от десятилетий до «Сейчас»

**Статус:** принято (Этап 8, до Gate C)
**Уточняет:** ARCHITECTURE.md §22–§27 (классы полномочий ИИ, Proposal, OrderedActionPlan, CurrentActionSelector); ADR-0004 (ИИ-мозг через MCP); ADR-0006 (Исполнятор); ADR-0008 (разборы)

## Контекст

Этап 8 показывает человеку не только `Сейчас`, но и причинную линию: куда ведёт сегодняшнее действие.
Продуктовая модель утверждена владельцем до реализации; эта ADR фиксирует, как она ложится на уже
существующую архитектуру, и только то, что пришлось добавить.

Принцип: **дальнее крупно, близкое подробно.** Одна карта жизни, без категорий:

```
десятилетия → 3 года → год → сезон (одна главная цель) → 1–3 проекта → этап → действие → Сейчас
```

## Решения

### 1. Что переиспользовано, что добавлено

| Понятие продукта | Реализация |
|---|---|
| Главная цель сезона | существующий `Season.focus` (+ `whyItMatters`, `startedAt`) |
| Проект сезона | существующий `Intention` (+ `status`, `position`, `whyItMatters`, `closedAt`) — **новой сущности «Project» нет** |
| История сезонов | таблица `season_history` (старый `focus` перезаписывался, из существующих данных его не восстановить); закрытые проекты берутся из самих `intentions` по времени |
| План по десятилетиям | `decade_plan_items` (`startYear`, `endYear`, короткое `statement`; порядок = `startYear`, диапазоны не пересекаются) |
| Горизонт 3 года / направление года | `three_year_horizon`, `year_direction` — по одной строке; «одна текущая» — факт БД (уникальный индекс на константу, как `work_intervals_one_running_idx`) |
| Утро / вечер | `routine_items` (kind, text, position, active) — самая маленькая модель; не Action, не часть плана, не рабочее время |
| «Курс изменён, нижнее не пересмотрено» | `course_changes` — только память напоминания, ничего не переписывает |
| Порядок, `Сейчас`, таймер, календарь, Proposal, change_log | без изменений |

Связь «слой → слой выше» — одно короткое предложение `whyItMatters` на нижнем слое (≤200 символов, может
быть пустым). Связь «3 года → десятилетие» не хранится: она **выводится** пересечением лет
(`decadesServedBy`).

### 2. Не больше трёх активных проектов — три уровня защиты

1. Домен: `changeIntentionStatus` / `hasRoomForActive` (`MAX_ACTIVE_INTENTIONS = 3`).
2. Приложение: типизированный результат `ACTIVE_PROJECT_LIMIT` (новый код в `APP_ERROR_CODES`; §29
   перечисляет «минимум»). Четвёртый проект не создаётся и не возобновляется молча; UI говорит по-человечески.
3. БД: триггеры `intentions_active_limit_insert/_update` (миграция 0017, custom SQL — как триггер
   `captures_raw_text_immutable`): ни Electron, ни MCP, ни будущий писатель не сможет получить четыре
   `active` строки, даже при гонке двух процессов.

Состояния: `active | deferred | completed | released`. Завершённый/отпущенный/отложенный не считается активным.
Завершённый или отпущенный проект можно вернуть **только на паузу** (`deferred`), никогда сразу в `active`:
возврат не обходит лимит и отменяет ошибочное «Завершить» (урок Этапа 2).
Любой переход из `active` в другое состояние в той же транзакции останавливает идущую на этом проекте работу
(как «Готово»/блокировка действия): время сохраняется, второй интервал не возникает.

### 3. Один `Сейчас` на несколько проектов — селектор не тронут

`CurrentActionSelector` остаётся чистой детерминированной функцией одного плана. `loadFocusState`
(`packages/application/src/map.ts`) только решает, **какой проект спросить первым**: порядок активных
проектов задаёт владелец вручную (`Intention.position`, `reorderProjects`); идущая работа закрепляет свой
проект (Этап 5 §7 — карточка не прыгает при перестановке); проект без допустимого действия пропускается.
Ничего не оценивается и не выдумывается. `NeedsAIReplan` — только когда ни один активный проект ничего не
может предложить; по каждому проекту отдельно виден `needsAiReplan`. Приостановленный проект никогда не
отдаёт работу «про запас». ИИ не получил никакого пути менять порядок проектов, их статус или состав.

`CurrentViewDto.intention/stages/orderedActionPlan/unplannedActionIds` описывают **фокусный проект**
(владельца `currentAction`, иначе первый активный) и дублируют его запись в `projects[]`; так прежние
потребители (MCP-контекст, тесты) работают как раньше.

### 4. Два режима стратегической правки

* **A. Уточнение формулировки** (`mode: "wording"`): тот же смысл, меняются слова. Годы не меняются (иначе
  `VALIDATION_ERROR`), ничего ниже не смотрится, ничего не помечается устаревшим.
* **B. Смена курса** (`mode: "course"`; для сезона — `startsNewSeason: true`): сначала `previewCourseImpact`
  показывает, что может быть затронуто (чистая функция `computeCourseImpact`: всё существующее строго ниже
  изменяемого слоя + активные/отложенные проекты со счётчиками этапов и действий); изменение применяется
  только вместе с `impactFingerprint` именно этого показа (иначе `REQUIRES_CONFIRMATION`). Если между
  показом и подтверждением что-то ниже изменилось — отпечаток не совпадёт и владелец смотрит заново. Если
  затронутого нет — подтверждать нечего.

Осознанное отклонение от буквы «представить через Proposal»: Proposal в этой архитектуре — предохранитель
полномочий **ИИ** (`createdBy: mcp-ai`, всегда про один Intention, `payload.intentionId`, отпечаток одного
проекта). Собственное решение владельца — не предложение ИИ; его подтверждением служит обязательный
предпросмотр последствий + отпечаток + атомарное применение (§44). Для ИИ путь остаётся прежним и
единственным: он не получил ни одного нового write-инструмента, а предложить пересборку маршрута проекта
может через существующий `create_route_proposal` — с подтверждением владельца.

Смена курса **ничего не переписывает ниже**: Intention, Stage, Action, OrderedActionPlan байт в байт те же
(тест `map.test.ts`). Остаётся запись `course_changes` (только если что-то затронуто) — на нём держится
предложение «Посмотреть, что нужно пересобрать» → «Попросить ИИ перестроить» (черновик в `+`, не
отправляется сам) → обычный route Proposal → подтверждение → «Всё пересобрано».
Идентификаторы всех записей о смене курса входят в `contextFingerprint`: после смены курса ожидавшие
предложения ИИ становятся `stale` (мир, о котором они рассуждали, изменился), а простое уточнение
формулировки — нет.

### 5. Честный прогресс

Только счёт явных вещей: «Этап 3 из 7», «4 из 6 действий», «Завершено 2 из 3 проектов сезона»
(`projectProgress`, `seasonProgress`; отпущенные не считаются завершёнными) и записанные доказательства
(`evidenceSince`, `evidenceForYears`: завершённые проекты, прожитые сезоны, по локальному году владельца).
Ни одного поля «процент/оценка» нет в контрактах; тест проверяет, что его нет и в разметке карты.

### 6. Границы ИИ

`PlanningContext` расширен: стратегическая линия, проекты с прогрессом, `projectSlots`. **Рутины в контекст
ИИ не входят** (`PlanningContextDtoSchema = CurrentViewDtoSchema.omit({ routines })`). Команды
`intention.changeStatus/reorder`, `strategy.*`, `routine.*` в `COMMAND_POLICY` имеют только `user-ui` и
`system`; тест фиксирует, что у `mcp-ai` остались ровно `proposal.create`, `plan.reorder`, `memory.save`.
`createRouteProposal`, `proposeDesiredResultChange`, `reorderExistingActions` отказывают для неактивного проекта.

### 7. Миграция 0017 (аддитивная)

Новые таблицы + `ADD COLUMN … DEFAULT` в `season` и `intentions`; custom SQL: `season.started_at` = время
последней объявленной владельцем смены сезона (`season.changeSeason`), иначе `created_at`; существующий
единственный Intention остаётся `active` с `position = 1` (он и был «активным замыслом» Этапов 2–7); триггеры
лимита. Ничего не выдумывается: новые слои пусты — это допустимое состояние. Перед миграцией desktop
делает обычный автоматический backup (`runMigrations`).

### 8. Что сознательно не делается

* Онбординг первого запуска (DEVELOPMENT_PLAN §4.9) — вне утверждённого владельцем контракта этого прохода.
* Ручное «время рутины», чекбоксы, серии, повторения — рутина это опора дня, не задача.
* ИИ-путь для стратегических слоёв (предложить год/сезон) — см. FUTURE_IDEAS.
* Визуальная полировка — Этап 9.

## Независимое ревью (Этап 8, до Gate C)

Первый проход (свежий ревьюер, 0 HIGH, 2 MEDIUM — оба подтверждены воспроизведением и исправлены):

* **M1. Смена курса десятилетия считала последствия только по старым годам.** Утверждение, переезжающее
  *в* годы текущей цепочки, проходило без подтверждения и без напоминания, а напоминание об утверждении,
  уехавшем *из* цепочки, пересчитывалось по новым годам и оказывалось пустым. Исправлено:
  `computeCourseImpact` принимает предполагаемые годы (`proposed`) — последствия есть, если пересекаются
  старые **или** новые годы; `previewCourseImpact` и `gateCourse` получают те же годы; напоминание о
  десятилетии пересчитывается для слоя целиком (`targetId = null`), потому что записывается только когда
  что-то было затронуто. Регрессионные тесты: домен (`strategy-map.test.ts`), приложение (`map.test.ts`).
* **M2. Уточнение формулировки сезона и перестановка проектов делали ожидающие предложения ИИ устаревшими**,
  вопреки «уточнение не каскадирует» и «порядок решает лишь, какой проект спросить первым».
  Исправлено: сезон входит в `contextFingerprint` как `id:startedAt` (настоящая смена сезона по-прежнему
  устаревает предложения), `intentions.reorder` не увеличивает `version` (порядок — не содержание).
  Регрессионные тесты: приложение и SQLite (`map.test.ts`).

Второй проход (только дельта исправлений): **одобрено, MEDIUM/HIGH не осталось.** Принято к сведению и
оставлено как есть: добавление нового десятилетия не гейтится (диапазоны не пересекаются, оно может лишь
занять свободные годы; «добавить» нигде в каноне не требует подтверждения); правка фокуса сезона с
`startsNewSeason=false` во что-то совсем иное остаётся уточнением по явному выбору владельца.
Проверено ревьюерами как надёжное: полномочия ИИ (ни одного нового write-инструмента, `mcp-ai` по-прежнему
только `proposal.create`, `plan.reorder`, `memory.save`), лимит трёх проектов на трёх уровнях, отсутствие
TOCTOU у гейта смены курса, неизменность селектора и таймера, аддитивность миграции 0017, рутины вне плана и
контекста ИИ, честный прогресс, пустые состояния.
